## Hierarchy, tenancy & clinic switching (brief sections 1, 3, 15)

**Maturity:** `partial` — built 2, partial 11, missing 9

Tenant isolation is the strongest thing in this codebase and is genuinely production-grade: 85 of 94 Prisma models carry tenantId, prisma/rls.sql enables + FORCEs a tenant_isolation policy on 86 tables, PrismaService refuses to boot on a BYPASSRLS role (prisma.service.ts:55-77), and three CI guards (check:rls, check:rls-live, check:isolation) keep it from regressing. ### Architectural risks

- User is single-tenant but the switcher is cross-tenant. User.tenantId is a scalar (schema.prisma:221) and User carries a tenantId-keyed RLS policy (rls-user.sql:39-42). The moment a genuine cross-tenant membership exists, the acting user's own User row becomes invisible in the tenant they switched into. That is not theoretical: org-hierarchy.service.ts:30-38 includes `user: { select: ... }` on a REQUIRED Prisma relation, so a cross-tenant membership makes GET /org/hierarchy/summary throw 'Field user is required to return data, got null'. Appointment.providerId (schema.prisma:513) FKs to User and would insert fine (Postgres FK checks bypass RLS) but resolve to nothing on read. The cross-tenant feature and the single-tenant User model are in direct contradiction; one of them has to move before any multi-clinic customer exists.
- Organization's RLS policy makes the organization tier unqueryable from inside a tenant. rls.sql:614-622 scopes Organization visibility through an OrganizationClinic row matching the current app.tenant_id. So org-level anything — consolidated dashboard, org settings, cross-clinic staff directory, org-wide audit — cannot be served from a normal forTenant() transaction. Every org-level feature will therefore need a bespoke SECURITY DEFINER function. rls-user.sql already has three; the file's own comment says 'it should stay that way — every addition is another thing that runs as the owner'. The brief demands a whole org-admin surface, so this pattern is on a path to a dozen definer functions, each one a hand-audited RLS hole. Consider instead a second GUC (app.organization_id) set from a validated membership, with org-tier policies keyed on it — one mechanism to audit rather than N functions.
- Tenant is being used for two different things at once. Today tenant == clinic == billing subject == RLS boundary == entitlement scope. The brief wants the ORGANIZATION to be the billing/ownership subject and the CLINIC to be the operating unit, with branches under it. Right now Subscription and TenantEntitlement both hang off tenantId (schema.prisma:430, :445), so a three-clinic owner gets three subscriptions and three separate entitlement sets that can silently drift — one clinic loses a module at renewal and nobody notices. Decide now whether entitlements are org-level with per-clinic overrides (the plan doc's TenantModuleOverride) or stay per-clinic; retrofitting after customers exist means a billing migration.
- Adding branchId to ~28 tables after data exists is a migration with a correctness trap, not a schema change. The nullable-then-backfill-then-NOT-NULL sequence is the easy part; the hard part is that RLS policies with no WITH CHECK reuse their USING expression as the INSERT check (documented at platform-tenants.service.ts:22-26), so a branch-aware policy will start rejecting writes from any code path that has not yet learned to set the branch GUC. That will surface as scattered 500s in unrelated modules. Sequence it: TenantCtx/middleware first, then columns nullable with app-level population, then policies, then NOT NULL.
- StockItem, VaccineBatch, Ward and Bed are physically per-location but modelled per-tenant (schema.prisma:762, :2946, :933, :946). A two-branch clinic sharing one StockItem row will show stock at a branch that does not have it, and the EPI cold-chain logic (VvmStage, schema.prisma:2917-2923) will attribute a fridge excursion to the wrong site. This is the branchId gap doing clinical rather than cosmetic damage, and it argues for doing inventory and vaccine batches in the FIRST branchId migration wave rather than the last.
- The clinic switcher's role escalation path is unguarded by any audit trail. auth.service.ts:199 mints a token carrying the membership's role, which may differ from User.role. AuditLog (schema.prisma:1190-1203) has no branchId, no membershipId, and nothing writes a row on context switch. When an org owner switches into a clinic as ADMIN and voids an invoice, the audit record cannot say which clinic-context they were acting under. Add a context-switch audit event and a branchId/membershipId column to AuditLog before the switcher is usable by a real multi-clinic customer.
- Entitlements and the sidebar are cached in localStorage keyed globally, not per context. AuthContext.tsx:33 uses a single ENTITLEMENTS_KEY and AppShell.tsx:67-71 filters nav from it. switchContext does refetch (AuthContext.tsx:128-131), but a failed /entitlements call falls back to an empty array (AuthContext.tsx:59-61), which silently renders an empty sidebar rather than an error — and with multiple clinics on different editions, a stale write from an in-flight request for the previous clinic can land after the switch. Key the cache by tenantId and treat a fetch failure as an error state, not as 'no modules'.

### Architectural risks

- Tenant IS the clinic, and Organization is a derived by-product. Every onboarding unconditionally inserts a new Organization (platform-tenants.service.ts:207-229) whose name is `${clinic} Organization` and whose code is machine-generated. The brief's model is client -> many clinics; the code's model is clinic -> auto-org. Every multi-clinic feature will fight this until onboarding accepts an organizationId.
- One human = one User row = one home tenant. User.email is globally unique and User.tenantId is a single scalar (schema.prisma:220-222), and the onboarding service deliberately rejects a reused email with a ConflictException explaining that one email means one account (platform-tenants.service.ts:147-149). An owner of three clinics therefore needs three separate logins — which defeats the context-switching machinery that was actually built (auth.service.ts:88-212). The membership table supports the intent; the identity model forbids it.
- Platform admins are invisible to their own data plane. tenantId=null plus FORCE RLS means every cross-tenant read needs either a grouped query over non-policied columns or a new SECURITY DEFINER function. Today there are exactly two sanctioned bypasses (auth_find_user_by_email, auth_find_memberships_for_user in prisma/rls-user.sql) and the codebase states a policy of not adding more. Quotas, usage dashboards, module matrices, support access and platform health ALL require this capability, so that policy will be tested repeatedly — better to design one audited platform-read function now than to accrete five.
- Entitlements are a frozen snapshot with no link back to the plan that sold them. TenantEntitlement.featureKey is a bare string with no FK to Feature (schema.prisma:443-453), and the rows are written once from featuresForEdition() (platform-tenants.service.ts:296-308). Editing EDITION_FEATURES in editions.ts changes what NEW clinics get and nothing about existing ones. Price and delivered features will drift apart silently, and there is no query that can tell you which tenants are on a stale bundle.
- Subscription is decorative. It has no startsAt, no unique constraint on tenantId (only @@index, schema.prisma:439), no cancel fields, and exactly one writer. A tenant can accumulate overlapping subscription rows with no defined winner, and when expiry enforcement is finally added there will be no reliable 'current' subscription to enforce against.
- Three parallel, unenforced status enums: TenantStatus (schema.prisma:52-57), OrganizationStatus (:59-63) and SubscriptionStatus (:65-70). None is read anywhere. Precedence between them is undefined, so the first enforcement PR will have to make a product decision under time pressure — e.g. does an ACTIVE tenant under a SUSPENDED organization log in?
- Branch exists as a table but not as a dimension. 2 of 85 tenant-scoped models carry branchId. The brief asks the platform admin to set branch limits and the plan doc's Phase A acceptance claims branch-scoped queries; neither is achievable without an ~80-table migration plus RLS policy rewrites. The longer clinical data accumulates, the more expensive that backfill becomes — this is the risk that compounds fastest.
- Module granularity is wrong for the price list. integrations.core alone bundles WhatsApp, Meta, FBR and telehealth; hr.core bundles HR and Payroll; pharmacy.core bundles Pharmacy and Inventory. The brief requires unpurchased modules to be individually hidden or locked, which the current key set cannot express. Splitting keys later is a data migration across every existing tenant's TenantEntitlement rows plus every @RequiresEntitlement decorator.
- Multi-Branch is entitlement-free. org-hierarchy.controller.ts:11-13 applies JwtAuthGuard + RolesGuard but no EntitlementGuard, so a SOLO-edition clinic can create unlimited branches and departments today. That is a revenue leak that also happens to be the exact module the brief wants gated.
- AuditLog exists and is dead. A model with no writers is worse than no model: it reads as delivered in the schema, in the plan doc's mental model, and to anyone doing a quick grep for 'audit'. It also lacks actor role, IP, user agent and before/after payloads — so support-access audit, which the brief makes a hard requirement, has no usable substrate.
- Onboarding straddles a transaction boundary it cannot close. Tenant is created outside the provisioning transaction because the tenant id is what the RLS context is set to, and failure is compensated by a delete with a logged worst case (platform-tenants.service.ts:126-153). Every field the brief adds to onboarding — N branches, quotas, module overrides, org attachment — widens that window and increases the chance of a half-provisioned client that only shows up as a support ticket.
- JWTs are never revalidated against the database. jwt.strategy.ts:53-68 does zero DB reads, and tokens carry tenantId, role and membership context. Suspension, deactivation, module revocation and quota lockouts will all be bypassable for the life of an already-issued token unless a status check is added to the request path or token lifetime is made very short.

### Architectural risks

- The role lives in the JWT and is trusted absolutely. app/backend/src/rbac/roles.guard.ts:38 and app/backend/src/common/tenant/tenant.middleware.ts:57 both copy the role claim through with no corroboration against the database. Every future authorization feature inherits this: any code path that can influence what goes into the `role` claim becomes an authorization bypass. POST /auth/switch-context is already such a path (app/backend/src/auth/auth.service.ts:199), and it was introduced by a feature — context switching — that had nothing to do with authorization. The next one will arrive the same way.
- UserRole is a Prisma enum, so 'configurable RBAC' is a compile-time property. Adding a role means a migration, a regenerate, a redeploy, and hand-edits to five arrays in app/backend/src/rbac/role-groups.ts. The brief needs 13 roles now and per-clinic custom roles later; both fight the enum. Worse, the enum is embedded in UserMembership.role (schema.prisma:350) and in the SQL return type of auth_find_memberships_for_user (app/backend/prisma/rls-user.sql), so the migration to a Role table touches the security-definer functions and the token minting path simultaneously — the cost of this refactor grows with every membership row written.
- Coarse role groups collapse distinct privileges into one list. app/backend/src/rbac/role-groups.ts defines five arrays; FINANCE_ROLES puts refund and void on the same footing as reading an invoice, and CLINICAL_ROLES puts RECEPTION inside the full EMR. The pressure to add a role to a group to unblock one screen will keep widening these lists, and each widening silently grants everything else the group protects. There is no test asserting which roles reach which route, so the widening is invisible in review.
- Branch exists in the hierarchy but not in the data. With 2 of 85 tenant models carrying branchId, every branch-aware requirement — per-branch reports, branch manager scope, per-branch stock, per-branch revenue share — is blocked behind a schema migration touching ~20 tables plus the RLS policies. Because the JWT already carries branchId (app/backend/src/auth/auth.service.ts:203) and the switcher already shows branch names in the UI (app/web/src/layout/AppShell.tsx:194), the system LOOKS branch-aware to a demo audience while enforcing nothing. That is the most dangerous configuration: it invites a customer commitment the data model cannot honour.
- RolesGuard is fail-open by design. app/backend/src/rbac/roles.guard.ts:23 returns true when no @Roles is present, which is why 39 of 207 handlers are open to every authenticated role. This is the opposite convention to EntitlementGuard, which is also fail-open (entitlement.guard.ts:27) but at least backed by a CI check (scripts/check-entitlement-coverage.ts). There is no equivalent check for role coverage, so a new controller with no decorator ships wide open and nothing goes red. Any permission system layered on top must invert this default or it inherits the same hole.
- Identity is fragmented across User, Employee and UserMembership with no owning entity. A person is a User (login, role), possibly an Employee (payroll, no FK to User), and possibly one or more UserMemberships (org placement, its own role that OVERRIDES User.role after a context switch). Three sources of truth for 'who is this person and what may they do', none authoritative. Reconciling them later is a data-migration problem, not a code problem, and it gets harder with every payroll run.
- There is no revocation anywhere. No way to deactivate a user, no way to deactivate a membership, no token invalidation, no password rotation, no session list. Once a credential or a role grant exists it is permanent short of direct SQL. For a healthcare product handling patient records under a staff turnover rate typical of clinics, this is a compliance problem as much as a security one — and it is the reason the escalation described above is not merely embarrassing but unrecoverable through the product.
- AuditLog exists as a model with zero writes. Every privileged action the brief wants permissioned — approve, refund, discount, export, view medical records — also needs to be attributable, and the table that would do it has been sitting unused since it was added. Retrofitting audit after the permission system is built means touching every mutation twice; it should land with the PermissionGuard, in the same interceptor.
- The org hierarchy API has no consumer. Branch, department and membership endpoints exist, are module-registered, and are called by nothing in app/web/src. Unconsumed API surface does not stay correct — it is not exercised by the safety suites either (only test/safety/tenant_onboarding_suite.py touches the platform module, and only its two tenant routes). The membership endpoint being both unused and the escalation vector is not a coincidence: nobody has had a reason to look at it since it was written.

### Architectural risks

- Appointment is a single flat table with no resource dimension. It has providerId only — no roomId, no equipmentId, no branchId, and only two indexes, @@index([tenantId]) and @@index([patientId]) (schema.prisma:524-525). A calendar's primary query is 'all bookings in this time window for this branch', which has no supporting index at all. Every calendar view will seq-scan the tenant's entire appointment history. Adding rooms later means either a nullable roomId (which cannot express 'this laser AND this nurse') or a join table that invalidates every conflict query written against the flat shape. Decide the resource model BEFORE the calendar screen is written.
- Clinical content lives in unvalidated Json blobs. NoteInstance.data (schema.prisma:1624), IntakeSubmission.answers (1604) and NoteTemplate.schema (1320) mean diagnoses, allergies, chief complaints and Fitzpatrick types are unqueryable. No report can answer 'how many patients are allergic to lidocaine', no rule engine can read a value, and no index can be built. Worse, EmrService.createNote (emr.service.ts:108-125) writes `data` through without checking it against the template schema, so a field marked required: true in the manifest (e.g. aesthetic.manifest.ts:90 consent_taken) can be silently absent. The Json layer is right for pack-specific long-tail fields and wrong for anything the business needs to count or the clinic needs to be safe about — those must be promoted to columns or to child tables.
- branchId reaches 2 of 85 tenant-scoped tables. Phase A built the hierarchy and the JWT carries branchId/departmentId, but no clinical or financial row records where it happened. Every branch-scoped calendar, day sheet, queue and report in the brief and in the plan doc's Phase D acceptance criteria is blocked on a backfill across ~40 tables. The cost grows with every row written between now and the migration — do this before onboarding a second branch, not after.
- Status enums with no transition guard, repeatedly. AppointmentStatus (schema.prisma:72-81) is enforced nowhere: updateStatus (appointments.service.ts:57-63) will move COMPLETED back to BOOKED. This codebase already lost real money to exactly this shape — the comment at emr.service.ts:201-208 documents a plan re-entering PROPOSED and being invoiced three times for 240,000 PKR. The same unguarded pattern is live on appointments today, and check-in/no-show/cancel timestamps will make it worse by allowing contradictory histories (checkedOutAt before checkedInAt).
- The tenant-verification helper is a copy-pasted convention, not an enforced invariant. `ensurePatient` is duplicated verbatim in 8 services (emr.service.ts:257, dental:492, imaging:275, immunization:373, ipd:213, lab:198, pharmacy, plus callers) and simply absent from appointments.service.ts. Because Postgres FK checks bypass RLS and `User` is deliberately unpolicied (rls.sql:30), any service that forgets the convention accepts cross-tenant foreign keys. This should be a Prisma middleware or a shared guard, not a function each author remembers to copy — the RLS coverage script (scripts/check-rls-coverage.ts) proved the value of making this class of drift fail the build.
- The React SPA and the legacy static demo pages have diverged, and the demo is the more complete product. app/backend/public/aesthetic-workspace.html is the ONLY consumer of encounters, intake, notes, treatment plans, consent and photo sessions. It is unrouted, unentitled, untested, hardcoded to packKey 'aesthetic', and linked from the backend index page (public/index.html:44) alongside login credentials. A demo that exercises paths the real app cannot reach is precisely how work gets reported as done — and it is also an unauthenticated-by-default surface shipped in the production image. Either port it into the SPA or delete it; leaving it is the risk.
- No screen-level test can catch a field-name contract break. Both PatientRecordPage bugs (startedAt vs occurredAt, invoiceNumber/totalPkr/issuedAt vs number/total/createdAt) survive because the vitest harness stubs those endpoints with `[]` (PatientRecordPage.test.tsx:39-40). The web layer hand-writes its response interfaces (app/web/src/api/types.ts) with nothing tying them to the Prisma types the API actually returns. As more sections land on the patient record, more will silently render blanks — on a chart, where the header comment at PatientRecordPage.tsx:8-12 correctly states that absence is read as evidence. Generate the client types from the API, or make every section test assert one populated row.
- Unbounded list endpoints are load-bearing for the whole UI. /patients has no take/skip and 12 screens fetch it in full. This is not just slow: it ships the tenant's entire patient roster to any authenticated role holding patients.core, including SALES and INVENTORY, on nearly every page view. Pagination is normally a scaling task; here it is also a data-minimisation one.
- Nothing in the clinical record is immutable. No signature, no lock, no amendment chain outside imaging (schema.prisma:1120-1131) and no signature outside EyeExam. A note can be created, and the schema offers no way to say it was approved, by whom, or that it has not changed since. Bolting signatures on after data exists means every pre-signature row is permanently unattributable — this needs to land before the first real clinic goes live, not in a later hardening phase.

## Services catalogue, billing, patient ledger (Brief Section 4)

**Maturity:** `partial` — built 7, partial 10, missing 23

What exists is a hardened single-invoice engine: itemized invoices, per-tenant hole-proof numbering under an advisory lock, row-locked payments with amount-validated idempotency, a PaymentIntent state machine for gateway links, refunds, attributed voids, and FORCE RLS on all seven billing tables. That part is genuinely production-grade and reachable end-to-end from app/web/src/pages/BillingPage.tsx. Measured against Brief Section 4, however, most of the demanded scope is simply absent: there is no tax anywhere (Invoice.total is one undifferentiated Int and the FBR payload hardcodes TaxRate: 0), no discounts, no quotations, no treatment packages or session tracking, no advance payments (Payment.invoiceId is NOT NULL, so a payment cannot exist without an invoice), no installments, no credit balance, no patient ledger or account statement, and zero insurance/corporate billing. ServiceCatalogItem carries 12 columns and is missing 13 of the attributes the brief names; it has no write API at all — the only writer is the pack seeder, which overwrites name/category/price on every re-activation. Critically, InvoiceLineItem has no serviceCatalogItemId and no performedById, so per-service revenue, commission attribution, session decrement and list-vs-charged variance are all blocked by two missing columns. One documented claim is false: billing.service.ts:34 states "a CHECK (paid <= total) backstops overpayment" — no such constraint exists in constraints.sql or any migration; the JS guard at billing.service.ts:414 is the only defence.

**Verifier verdict:** Over-claimed, moderately. Most of the auditor's file:line citations are accurate and its "partial" ratings are honest — the overpayment / phantom-CHECK finding in particular is correct and important (I grepped every migration and constraints.sql: the only ADD CONSTRAINTs are foreign keys, there is no CHECK anywhere, so billing.service.ts:34's docblock is a lie in the source). One "partial" carries a factually wrong reason (appendLine does have a controller route). Several "built" notes materially understate what is broken: the refund UI hardcodes CASH, the void UI never sends a reason, the payment UI never sends a reference, and serviceCatalogItemId is validated then silently thrown away. The auditor also ignored roughly two-thirds of brief section 4 outright.

### Architectural risks

- Invoice.total is a single denormalized Int (schema.prisma:533) with no subtotal/discount/tax decomposition. Every additional money concept the brief demands — tax, discounts, payer split, package allocation — requires restructuring this column and every historical row. This is the highest-cost retrofit in the domain and it gets more expensive with every invoice written. Restructure before the product carries real invoices.
- Two missing columns on InvoiceLineItem (schema.prisma:597-617) — serviceCatalogItemId and performedById — independently block per-service revenue reporting, commission attribution, package session decrement and list-vs-charged variance. The DTO already accepts serviceCatalogItemId (create-invoice.dto.ts:21) and buildLines silently drops it (billing.service.ts:449-473), so the API contract currently lies about what it stores.
- Prices are client-supplied and never reconciled with the catalogue. unitPricePkr, lateralizable and bilateralPricePkr all come from the request body (create-invoice.dto.ts:35,54,61); expandLaterality prices from those values (laterality-pricing.ts:71-81) rather than from the ServiceCatalogItem row. The catalogue is therefore advisory, price integrity is nil, and no report can distinguish a discount from a typo.
- Payment.invoiceId is NOT NULL (schema.prisma:622). Advances, deposits, credit balances and unallocated receipts are structurally impossible, not merely unbuilt. Any fix makes the column nullable and changes the meaning of every existing payment query and reconciliation path.
- Zero of the 7 billing tables carry branchId; only 2 of 85 tenant-scoped models have it at all (Department schema.prisma:325, UserMembership :348). Phase A delivered the hierarchy but did not thread it into money. Multi-branch clinics — the entire premise of the org hierarchy work — cannot have per-branch price lists, per-branch tills, per-branch P&L or per-branch invoice series. The cost of adding branchId grows with the data.
- Two disjoint money systems. Clinic revenue lives in Invoice/Payment; pharmacy revenue lives in Dispense (schema.prisma:779-796) with its own receipt series, its own paymentMethod and no invoice. reports.service.ts:95-100 papers over the split by summing them side by side. A patient's true balance cannot be computed, refunds cannot cross the boundary, and FBR filing covers only one of the two.
- Pack seeding is destructive to catalogue data: pack-seeding.ts:39-46 overwrites name, category, pricePkr, durationMin, lateralizable and bilateralPricePkr on every activation. The moment clinics can edit their own prices, a routine pack version upgrade silently reverts them. A source/override discriminator must land before, not after, the catalogue editor.
- FBR tax identity is process-global (fbr.service.ts:39 reads config.integrations.fbr). Every tenant in a deployment would file under one NTN and POS ID. Combined with the hardcoded TaxRate: 0 and PCTCode '0000.0000' (fbr.service.ts:157-158), the integration is not merely stubbed — it would file materially incorrect returns the moment credentials are supplied. The stub honestly reflects missing credentials; the payload does not honestly reflect missing tax modelling.
- Money is int4 PKR throughout (MAX_INT4 guards at billing.service.ts:18, 329, 464, 471; emr.service.ts:147, 162). A per-invoice ceiling of PKR 2.15bn is fine for a clinic bill but not for corporate/insurance monthly batch invoices or annual aggregates, which is exactly the direction the brief points.
- Whole-controller RBAC on money. FINANCE_ROLES (rbac/role-groups.ts) includes RECEPTION, so cash handling, refunds, voids and free price entry are one permission. The plan doc names refund and discount as distinct actionKeys (docs/universal-saas-gap-to-backlog.md:127) but schedules no billing work to enforce them. The inverse problem is already visible: DOCTOR is 403 on all billing routes, forcing dental completion to bill through a service-layer back door (billing.service.ts:312, dental.service.ts:391) — a pattern that will be copied by every future pack.
- No tenant-wide invoice or payment query surface. billing.controller.ts offers only per-patient list (:39) and get-by-id (:44), so the day-book, receivables aging and cashier reconciliation screens have no data path — and adding them later without branchId and without a ledger means writing them twice.
- Documentation drift in the money code. billing.service.ts:34 asserts a DB CHECK constraint that does not exist. The billing service is the most carefully commented file in the repo and its comments are treated as a safety record; a stale claim there is more dangerous than an uncommented gap, because it is read as verification.

### Architectural risks

- Mutable quantityOnHand with no movement ledger is the root risk. StockItem.quantityOnHand is decremented in place (pharmacy.service.ts:167-170) and the row has no updatedAt. Valuation, audits, adjustments, transfers, wastage and COGS all require a movement history that does not exist, so every one of them will be blocked on the same refactor. The longer real dispensing data accumulates, the more expensive the backfill becomes — and the backfill is only partially possible, because receives and dispenses are the ONLY events that were ever recorded.
- Stock has no location, and the org hierarchy that was just built makes that worse rather than better. Phase A added Organization -> Clinic -> Branch -> Department and a context switcher, but branchId reached only 2 of 94 models (Department at schema.prisma:325, UserMembership at schema.prisma:348) and 0 of the 85 tenant-scoped data models. The product now PROMISES multi-branch in its navigation and its context API while the inventory (and every other) data table remains tenant-flat. Selling multi-branch on this footing means a two-branch customer's stock figures are wrong from day one in a way no report can detect.
- The item master is compiled into the binary. FORMULARY (formulary.ts:13-22) is a global 8-row constant shared by every tenant, and receiveStock() hard-rejects anything outside it (pharmacy.service.ts:28-29). This directly contradicts the platform's own stated architecture ('core is shared, specialty is configuration') — every other configurable surface in this codebase is a tenant-scoped table seeded from pack manifests, and inventory alone is a hardcoded array. It also means selling price is a global constant: every clinic in Pakistan sells paracetamol at Rs 5 and cannot change it (pharmacy.service.ts:95-96).
- Two divergent inventory engines already exist and will keep diverging. VaccineBatch has discard, storage location, dose counts, VVM staging and a real alerts endpoint; StockItem has none of those. Their picking strategies differ deliberately and correctly (FEFO vs VVM-priority, cold-chain.engine.ts:93-116). But injections, dental materials and lab reagents — all named in the brief — will land in one silo or the other by accident, and total stock value already requires summing two systems that share no code, no ledger and no valuation.
- Expired stock is flagged but never removed, so the inventory is permanently overstated. Expired units stay in quantityOnHand forever (there is no write-off path and no discardedAt column on StockItem), while the read path correctly excludes them from onHand (pharmacy.service.ts:76-78). The database therefore holds a number that no screen shows and that any future valuation query will pick up. Whoever builds valuation will inherit an already-wrong opening balance.
- Consumption is invisible to clinical and financial workflows. Dispense links to a patient and nothing else — no encounter, appointment, procedure, prescription, department or recipient (schema.prisma:779-796). Consequences that will bite as the product grows: procedure profitability cannot be computed; the plan doc's PERCENT_NET_AFTER_CONSUMABLE commission basis (universal-saas-gap-to-backlog.md:258) is uncomputable; a prescription can never be marked dispensed (PrescriptionStatus.COMPLETED at schema.prisma:2806 is unreachable, dosing.service.ts:168 only ever creates); and department-level cost control is impossible.
- Pharmacy revenue bypasses the fiscal and refund machinery. A Dispense creates no Invoice and no Payment (schema.prisma:779-796), while FBR submission is invoice-keyed (integrations/fbr/fbr.service.ts:16). Pakistan-first positioning plus an FBR digital-invoicing integration plus an un-fiscalized retail counter is a compliance exposure that grows with every sale, and it also means a mis-dispense has no reversal path at all — no void, no return, no refund.
- RBAC is too coarse for goods custody. The entire pharmacy controller carries one @Roles(...PHARMACY_ROLES) at class level (pharmacy.controller.ts:25) including RECEPTION and DOCTOR (rbac/role-groups.ts:33-39), so anyone who can dispense can also book in stock and set its cost. Once adjustments, write-offs and counts exist, the same coarse gate would let a receptionist write off inventory. This is precisely the branch-scoped permission matrix the plan doc identifies as missing — and inventory is where its absence becomes a theft-and-shrinkage problem rather than a UX one.
- Receipt numbering is derived from a COUNT. nextReceipt() (pharmacy.service.ts:260-269) takes an advisory lock, counts existing dispenses with a year prefix, and returns count+1. The unique constraint (schema.prisma:794) makes a collision a hard error rather than a silent duplicate, which is the right failure mode — but any future void-by-delete, archival, or per-branch numbering requirement breaks it immediately. A sequence or a dedicated counter row scoped by tenant+branch+year is the durable shape.
- Concurrency safety is currently correct but hand-rolled and fragile. Deterministic lock ordering by formularyCode plus SELECT ... FOR UPDATE (pharmacy.service.ts:134-139) is the right fix for the deadlock it documents. Every new write path — transfers, adjustments, issues, counts — must reproduce that discipline by hand, against a raw SQL string that hardcodes the table name "StockItem" and the column "formularyCode". Renaming either during the item-master migration will break the lock silently: the query would fail loudly, but a partially-updated variant that locks the wrong rows would not.

### Architectural risks

- THE CENTRAL RISK — specialty depth lives in the schema, not in config. 30 specialty-specific tables exist today: Dental 7 (ToothRecord schema.prisma:667, PerioExam:2154, PerioToothRecord:2173, ToothPlanItem:2196, OrthoCase:2222, OrthoEvent:2246, ToothFinding:2873), Ophthalmology 6 (EyeExam:2348, VisualAcuityMeasure:2373, Refraction:2392, IopMeasurement:2413, EyeSegmentFinding:2433, OpticalPrescription:2453), ObGyn 6 (PregnancyEpisode:1852, AncVisit:1899, ObstetricUltrasound:1939, Partogram:1982, PartogramEntry:2008, GynaeProfile:2046), Rehab 5 (RehabEpisode:2505, MskAssessment:2534, RomMeasurement:2556, RehabSession:2578, ExercisePrescription:2602), Dermatology 3 (PhototherapyCourse:2654, PhototherapySession:2695, SkinLesion:2732), Immunization 3 (Immunization:639, VaccineBatch:2946, Aefi:2981). Against that, the entire configuration engine is 6 tables (ServiceCatalogItem, NoteTemplate, IntakeFieldGroup, OrderSet, TrendChartDefinition, DoseRule). 5:1 against the brief's stated principle. Growth is also unbounded: 47 of the schema's 74 enums are specialty-specific (ObGyn alone contributes 22, schema.prisma:1682-1852; Ophthalmology 10, schema.prisma:2274-2346), and every new clinical vocabulary term is a Prisma enum change requiring a migration and a deploy.
- Adding a specialty is a core rebuild, measured on the Ophthalmology precedent: 216 lines of schema.prisma (lines 2274-2489, 6 models + 10 enums), 24 statements in prisma/rls.sql, 8 TypeScript files totalling 618 LOC in app/backend/src/ophthalmology (module + service + controller + 3 engines + DTOs), 9 controller routes, a 359-LOC hand-written React page (app/web/src/pages/OphthalmologyPage.tsx) plus a 374-LOC test, an App.tsx route entry, a nav.ts entry with a literal entitlement string, an Edition enum value, a feature key and bundle in entitlements/editions.ts, and only then a 132-LOC manifest. The brief promises configuration-only onboarding; the actual cost is a migration + a NestJS module + a React page + three files edited in the frontend shell. The plan doc's Phase E acceptance criterion ('new specialty onboarding is manifest/config work, not core rebuild') is currently unachievable.
- The frontend is completely disconnected from the config engine. app/web/src has ZERO references to /intake-groups, /note-templates, /order-sets, /service-catalog or /packs. Whatever a pack seeds into a tenant is invisible in the product. The only working demonstrations of config-driven rendering are two static HTML files (app/backend/public/aesthetic-workspace.html, pediatrics-workspace.html) that the React port left behind — so the system's config capability has REGRESSED relative to its own earlier demo. Anyone reading the backend alone will substantially over-estimate maturity.
- Pack re-activation destroys tenant customisation. seedPackForTenant (pack-seeding.ts:30-148) upserts on (tenantId, key) and overwrites name, fields, schema, items and chart bands on every activation. The comment at pack-seeding.ts:121-122 acknowledges this ('a tenant edit survives until the pack is re-activated'). The moment a form builder ships, publishing a pack update will silently wipe every clinic's customised form. A copy-on-write / customisation-flag model must land BEFORE or WITH the builder, not after.
- Two parallel instrument engines, and the manifest advertises the wrong one. instruments/instrument.engine.ts scores from InstrumentDefinition rows (data); dermatology/engines/grading.engine.ts hard-codes PASI (line 92), EASI, SCORAD, MASI and VASI and serves them from TS constants via a separate endpoint (dermatology.controller.ts:25). dermatology.manifest.ts:135-142 lists pasi/easi/scorad/masi/vasi as shared-library instrument refs — none of those keys exist in InstrumentDefinition, and pack-seeding.ts never reads manifest.instruments anyway, so the discrepancy is invisible. Any future work that trusts manifest.instruments will break.
- InstrumentDefinition is global (schema.prisma:1256-1265, no tenantId). Structurally, a clinic can never have its own questionnaire. This is a schema-level ceiling on the brief's 'assessment forms' requirement that no API work can lift.
- Clinical rules are compiled constants, so a rule change is a deploy, and clinical rules change often. The phototherapy protocol (NBUVB_STANDARD, phototherapy.engine.ts:90-92) and the electrotherapy contraindication list (modality-safety.ts:37-56) cannot be adjusted per clinic or per country guideline. Worse, there is no shared rule-firing audit: a WARN from rehab or obstetrics exists only in an HTTP response and is never persisted, so 'which warnings did the doctor see and dismiss' is unanswerable for most of the product. Only phototherapy (PhototherapySession.decision, schema.prisma:2716) and dosing (DoseCalculationLog, schema.prisma:2077) record anything.
- Migrating hard-coded rules to a data engine is a clinical-safety hazard in its own right. dermatology/engines/phototherapy.engine.ts:15-47 documents three successive generations of that engine producing MORE UV for a worse reaction, all caused by rule-ordering / early-return semantics. A generic ClinicalRule evaluator with first-match-wins or priority-ordered semantics would reintroduce exactly those bugs across every specialty at once. The generic engine must adopt 'every applicable rule contributes a candidate, most conservative wins, single clamp at a single exit' as its contract, and the derma safety suite must be re-run against the generic path before the hard-coded one is deleted.
- Clinical JSON is written with no schema enforcement. IntakeSubmission.answers and NoteInstance.data are accepted as unvalidated objects (emr/dto/create-intake-submission.dto.ts, create-note-instance.dto.ts — only @IsObject + a size bound), templateKey is free text, and templateId is never verified against templateKey or the tenant. There is also no formVersionId stamped on the submission, so once a template changes, previously filled notes can no longer be rendered faithfully — a medico-legal problem in a clinical record, and one that gets strictly worse the moment forms become editable.
- Phase A hierarchy and the config layer do not meet. Branch and Department exist (schema.prisma:288-341) but NO config table carries branchId or departmentId — not NoteTemplate (1311), IntakeFieldGroup (1329), OrderSet (1345), ServiceCatalogItem (1285), TrendChartDefinition (1369) or DoseRule (2768). A multi-branch group therefore cannot have different forms, price lists or protocols per branch, which is the primary reason such a group buys a multi-clinic product.
- Entitlement keys and manifests have drifted. entitlements/editions.ts declares 'pack.pediatrics' and a PEDIATRICS edition bundle, but manifests/index.ts:12-19 registers only 6 manifests and pediatrics is not among them. A PEDIATRICS-edition tenant is granted an entitlement that activates nothing — the onboarding loop at platform-tenants.service.ts:313-339 simply skips it. Nothing detects this: there is no startup assertion that every pack.* feature key has a corresponding manifest.
- Documentation and code comments over-state what is wired. schema.prisma:1367 says trend charts are tenant-tunable 'without a deploy' (no write API exists). dosing.controller.ts:30 says tenant formulary edits show up in the API (no write API exists). platform-tenants.service.ts:311 says activation seeds 'service catalog, instruments and config' (instruments are never seeded). These are the exact kind of claims that have burned this owner before; they should be corrected in place as part of any config-engine work.

### Architectural risks

- SINGLE-TENANT INTEGRATION CREDENTIALS. whatsapp.service.ts:40-48 captures this.cfg in the constructor of a default-scoped (singleton) Nest provider, sourced from process.env at configuration.ts:80-84. There is no tenantId anywhere in the send path. The moment one real Meta credential is configured, every tenant on the deployment sends from that one clinic's WhatsApp number, and inbound replies land in a mailbox with no tenant to route them to. The stub policy has hidden this because the stub is also tenant-agnostic and nobody notices. This will actively fight the brief's 'Integration optional and enabled per client' at the very first paying integration customer, and it is not a small refactor: FbrService and TelehealthService have the identical shape, so the fix is a cross-cutting change to how integration config is resolved.
- NO PERSISTENCE ON THE OUTBOUND PATH. whatsapp.service.ts:75-87 returns a result object and writes nothing — not a Message row, not an AuditLog row. Every message sent before the conversation model lands is permanently unrecoverable. Because the brief requires conversation history linked to leads and patients, and because Meta requires opt-out honouring, the value of the audit trail is retroactive: you cannot reconstruct January's sends in March. This makes the message-log table the highest-urgency item even though it is not the most complex.
- LEADSTATUS IS A PRISMA ENUM IN A CONFIGURATION-DRIVEN PRODUCT. schema.prisma:987-993 hard-codes the pipeline. The whole thesis of this codebase — 'core is shared, specialty is configuration', delivered through pack manifests in src/packs/manifests — explicitly does NOT extend to CRM: grep of app/backend/src/packs for 'lead' or 'crm' returns zero hits. A dental clinic and an aesthetics clinic will want different stages, and today that is a schema migration plus a frontend enum change (CrmPage.tsx:31, 48-63 duplicates the enum client-side). Every additional stage the brief needs makes this more expensive to undo.
- NO SCHEDULER PRIMITIVE AT ALL. Zero hits for @Cron, ScheduleModule, BullMQ, agenda or setInterval across app/backend/src. Three named section-10 requirements (appointment reminders, payment reminders, follow-up messages) plus webhook retry, Meta page-token refresh before its 60-day expiry, and the nightly overdue-followup sweep all need it. Because it is absent, each of those features looks small in isolation and is not — the first one to be attempted pays for the whole substrate.
- AUTHENTICATION MODEL HAS NO UNAUTHENTICATED PATH. Every controller in app/backend/src is behind JwtAuthGuard, and tenant context comes from the JWT via TenantMiddleware into AsyncLocalStorage. Inbound webhooks and public website forms arrive with no JWT and must resolve tenantId from provider identifiers instead. That is a genuinely new auth path, and getting it wrong is a cross-tenant write. This is why the ingestion gap is XL rather than L, and it is the reason four of the eight lead sources in the brief are structurally unreachable today rather than merely unbuilt.
- UNGUARDED STATE TRANSITIONS CAN PERMANENTLY CORRUPT A LEAD. crm.service.ts:86-92 writes any status. Setting CONVERTED via PATCH leaves convertedPatientId NULL and then crm.service.ts:132-134 rejects the genuine convert() forever with 'Lead is already converted'. The lead is unrecoverable through the API. The UI happens not to offer this (CrmPage.tsx:57-63) which is exactly why it will survive manual testing. Note the contrast with convert() itself, which is carefully locked and race-proof — the rigour was applied to one route and not its neighbour.
- NO OWNERSHIP SCOPING IN THE SERVICE LAYER. crm.service.ts:67-75 returns every lead in the tenant to any of OWNER/ADMIN/SALES/RECEPTION (crm.controller.ts:24). The brief's role matrix requires salesperson = own + unassigned. The existing RBAC is role-only with no permission table and no row-level ownership concept, so this cannot be expressed with @Roles() — it needs service-layer filtering that does not exist for any module yet. Commission disputes make this urgent: a salesperson who can see and claim any lead can also re-attribute commission.
- ATTRIBUTION DATA IS DESTRUCTIBLE. Lead has no deletedAt and no unique constraint on phone (schema.prisma:995-1012), while Patient does carry @@unique([tenantId, mrn]) (schema.prisma:506). Funnel, source ROI, salesperson performance and commission all read from Lead history. A hard delete or a wave of duplicate ad leads silently rewrites financial attribution with nothing to detect it.
- ENTITLEMENT GRANULARITY MISMATCH. One key, integrations.core (editions.ts:38), covers WhatsApp, FBR e-invoicing and LiveKit telehealth together — three products with completely different commercial value in Pakistan. And editions.ts:65 vs :125 means the CLINIC edition ships crm.core WITHOUT integrations.core, so the mainstream small-clinic edition has a CRM that cannot send a message. As soon as WhatsApp is real, this bundling forces either giving FBR away or withholding WhatsApp from the edition most likely to want it.
- NO BRANCH DIMENSION ON ANY TRANSACTIONAL TABLE. 2 of 85 tenant-scoped models carry branchId, both hierarchy tables (Department schema.prisma:325, UserMembership schema.prisma:348). Phase A delivered the org tree but no data table was made branch-aware. For CRM specifically this means branch sales targets, branch commission pools and branch funnel comparison are all blocked on a wide backfill migration — and the longer Lead rows accumulate without branchId, the more guesswork that backfill becomes.

### Architectural risks

- Money is stored as Int PKR with a hard MAX_INT4 = 2,147,483,647 ceiling (billing.service.ts:18,329,464,471). Invoice totals are bounded and rejected cleanly, but PayrollRun.totalNetPkr (schema.prisma:889) has NO such bound — a 100-employee clinic is far from the ceiling, but a consolidated ORG-level payroll or annual rollup across clinics overflows int4 at ~PKR 2.1bn with no guard anywhere. Any org-level financial aggregate must be BigInt from the start.
- Whole-rupee integers with no decimals mean every percentage-based commission will silently truncate. 30% of PKR 18,333 is 5,499.9 — rounded per line, per staff member, per month, across a year, the residue is real and unattributed. The rounding policy (per-line vs per-payslip, floor vs half-up, and where the remainder lands) must be decided BEFORE the commission engine is written, and the residual must be posted somewhere explicit, or the clinic share silently absorbs it and no ledger balances.
- Commission recognised on INVOICE versus on PAYMENT is the single most consequential unmade decision in this domain. Invoice.paid is a mutable running total (billing.service.ts:249,439) that a refund DECREASES, and the refund path already deliberately collapses a refunded invoice to be byte-identical to a never-paid one (billing.service.ts:251-258). If commission is computed from Invoice.paid, a refund after a finalized payroll run creates a paid commission on money the clinic returned, with no clawback path and no record that it happened. Earnings must be an append-only ledger keyed to individual Payment and Refund rows, with negative entries for reversals — never a recomputation over a mutable balance.
- Employee and User are two unlinked populations (schema.prisma:859 has no userId). Every clinic will end up with duplicate identities for the same doctor, and reconciling them AFTER payslips and appointments both reference the divergent rows is far more expensive than adding the FK now. The schema already learned this lesson once for patients (the MRN uniqueness comment at schema.prisma:470-474 describes exactly this split-record failure) and has not applied it to staff.
- branchId is absent from all 85 tenant-scoped business tables. Phase A built the hierarchy but wired it to nothing transactional, so every branch-scoped requirement in the brief (branch revenue, branch attendance, branch P&L) requires a schema-wide migration + backfill later — across Invoice, Payment, Refund, Dispense, Appointment, Encounter and more. The cost of this grows linearly with production data and it is the classic 'add the dimension before the rows exist' decision. It is also a correctness risk: a backfill that guesses a branch for historical invoices manufactures financial history.
- The RLS model is tenant-only. Once branchId lands, branch-level access control (a branch manager who must not see another branch's payroll or revenue) has no enforcement layer — RolesGuard is a flat role enum (rbac/roles.guard.ts) with no scope, and UserMembership.branchId (schema.prisma:348) is recorded but consulted by nothing outside org-hierarchy.service.ts. Payroll is precisely the data where a scope leak is a resignation-level incident, and today any FINANCE user in the tenant sees every salary in every branch.
- Payslip is a fixed 4-column shape. Adding the 8 missing components as columns produces a wide, sparse, migration-per-feature table; the correct shape is a component child table. Deciding this AFTER a client has finalized runs means either a data migration of live payroll records or two parallel representations. This is a now-or-never structural call.
- Employee.designation is free text (schema.prisma:863). Commission rules will inevitably want to key off role/designation ('all technicians get 10%'). String matching against typo-prone free text as a commission input is a defect generator that pays the wrong people real money.
- Setting an employee ON_LEAVE removes them from payroll entirely (hr.service.ts:95 filters status:'ACTIVE'). For PAID leave this is silently wrong — the flag was designed as a roster marker and is being used as a payment gate. When real leave management arrives, this coupling must be broken deliberately or a genuine leave-management feature will start withholding wages.
- reports.service.ts runs 13 unfiltered, unbounded aggregates over the tenant's full history on every dashboard load (lines 41-55). With no date bound and no index on createdAt for these paths, this degrades continuously as a clinic accumulates data — and the fix (date ranges) is the same work as the brief's period-reporting requirement, so it should be done once, deliberately.
- Reporting reads Invoice.paid and Payment.amount as parallel sources of the same truth (reports.service.ts:44,46). billing.service.ts maintains the invariant payments − refunds == paid carefully, but nothing asserts it. A finance and commission engine built on top of two sources that are only conventionally equal will eventually disagree, and the disagreement will surface as a wrong commission cheque. Add a reconciliation check before layering on it.
- There is no stub or abstraction seam anywhere for attendance hardware. The rest of the codebase deliberately stubs third-party integrations behind a service boundary (integrations/fbr, WhatsApp, telehealth) so credentials are never fabricated — attendance has no equivalent, so when a camera vendor is chosen there is no seam to plug into and the ingest path will be designed under deadline pressure. Define the AttendanceDevice provider interface now, even with only a manual-punch implementation behind it.

### Architectural risks

- BRANCH BLINDNESS IS THE COMPOUNDING DEBT. 85 tenant-scoped models exist; branchId appears on exactly 3 rows in schema.prisma (Department.branchId:325, UserMembership.branchId:348, UserContextPreference.lastBranchId:375) and on zero transactional tables. Every day of feature work adds more branch-unaware rows and more write paths to retrofit. The brief's headline multi-branch requirement (consolidated AND branch-level views, branch comparison) cannot be partially delivered — it is all-or-nothing on this migration, and the migration touches RLS policies that are the product's core security guarantee.
- REPORTING HAS NO ARCHITECTURE, ONLY TWO HARDCODED QUERIES. reports.service.ts is 103 lines with two methods that take no arguments (summary():24, revenue():79) and reports.controller.ts:18-26 declares no @Query. Growing this to 20 parameterised, filterable, exportable, entitlement-scoped reports by extension means 20 bespoke controller methods and 20 bespoke React pages. Without a report-descriptor abstraction introduced NOW, the reporting surface becomes the largest untestable blob in the codebase.
- prisma.forTenant PINS ONE TENANT PER TRANSACTION (reports.service.ts:26, 81), WHICH DIRECTLY OPPOSES 'MULTI-BRANCH OWNERS NEED CONSOLIDATED VIEWS'. Every cross-clinic aggregate the brief demands has to escape the tenant-per-transaction model. The only existing escape hatch is the platform-admin path that deliberately bypasses forTenant (platform-tenants.service.ts:49-55) and is guarded by PLATFORM_ADMIN. An organization owner is neither a platform admin nor a single-tenant user — there is no third posture, and inventing one carelessly is how cross-tenant leaks happen.
- MONEY HAS NO ACTOR. Invoice (schema.prisma:528-561) has no providerId and InvoiceLineItem (schema.prisma:597-618) has no performedById. Doctor performance, doctor earnings, commissions and revenue share are not 'unbuilt reports' — they are unrecoverable from historical data. Every invoice raised between now and the schema fix is permanently unattributable, so the P&L by doctor will have a hole exactly the size of the delay.
- RBAC IS A SINGLE ENUM WITH NO SCOPE. RolesGuard + @Roles is the whole model; grep confirms no Role/Permission/RolePermission/MembershipScope tables exist despite the plan doc specifying all four (docs/universal-saas-gap-to-backlog.md:116-144). Reports are gated at reports.controller.ts:13 to OWNER/ADMIN/FINANCE wholesale. There is no way to express 'this doctor sees only their own performance', 'this branch manager sees only Branch B', or 'this receptionist may view but not export'. Every report added under the current model is an all-or-nothing disclosure decision.
- NAV IS A COMPILED CONSTANT. app/web/src/layout/nav.ts:48-83 is a hardcoded TypeScript array. Adding a clinic-configurable module set, per-branch menus, or 20 report entries means editing and redeploying the frontend. This directly contradicts the plan doc's Definition of Done item 4 ('configurable by admins without code deployment', docs/universal-saas-gap-to-backlog.md:578).
- FRONTEND ENTITLEMENTS ARE CACHED IN localStorage AND USED TO RENDER CHROME. AuthContext.tsx:39,51 reads healthos.entitlements from localStorage on rehydrate and the nav renders from it before the network refresh completes (AuthContext.tsx:86-90). A downgraded tenant sees stale modules briefly, and a hand-edited localStorage entry renders nav items the tenant never bought. The server-side EntitlementGuard still blocks the data, so this is a lying-UI defect rather than a breach — but as the module catalog grows, so does the number of dead links a user can reach.
- SIX FULLY BUILT BACKEND MODULES ARE UNREACHABLE FROM THE PRODUCT: appointments (appointments.controller.ts:28-61), media/photos (media.controller.ts:50-103), imaging (imaging.controller.ts:31-69), service catalog write path (catalog.controller.ts:18, read-only), org hierarchy branches/departments/memberships (org-hierarchy.controller.ts:22-35), and encounters outside the patient record. Editions bundle and bill for several of these. This is the exact failure mode the owner has been burned by — the backend audit will call them built and the customer will call them missing, and both will be right.
- THE 108-FILE STATIC PROTOTYPE AT frontend/screens/ IS AN ACTIVE REPORTING HAZARD. It contains appt-calendar.html, attendance.html, revshare-config.html, reports.html, cp-mrr.html, inventory-alerts.html and 102 more — precisely the screens this audit finds missing — with zero fetch/axios/XHR calls in any of the three sampled files. Plus docs/admin-dashboard-mockup.html (652 lines). Anyone reviewing the repo by screenshot will conclude the product is 5x more complete than it is.
- NO CHART LIBRARY, AND TWO BESPOKE SVG RENDERERS ALREADY EXIST (GrowthChartPage.tsx:197, TrendsPage.tsx:237). The path of least resistance is a third, fourth and twentieth hand-rolled chart, each with its own axis maths and accessibility story. Decide the charting strategy before ReportCenterPage is written, not after.
- DESKTOP-ONLY CHROME. AppShell.tsx:77 permanent Drawer, fixed 248px (AppShell.tsx:39), no breakpoint. A Pakistan-first clinic product where reception, doctors and owners work from tablets and phones cannot ship a shell that assumes a 1440px viewport. The cost of fixing this rises with every screen added on top of it.
- PLATFORM ADMIN HAS EXACTLY ONE ROUTE AND A HARD REDIRECT. DashboardPage.tsx:27 sends isPlatformAdmin users to /admin/tenants and nav.ts:97-102 gives them a single nav item. There is no platform information architecture to extend — organizations, subscriptions, MRR, quotas, support access and audit all need routing, nav grouping and a dashboard that currently have nowhere to live.
- UNBOUNDED PLATFORM QUERIES. platform-tenants.service.ts:52-59 does an unpaginated tenant findMany plus a full-table groupBy over Patient and User on every page load of TenantsPage, and TenantsPage.tsx:250 renders all rows. Correct at 10 clinics; a full-table scan per pageview at 1,000.
