# HEALTH OS — FRONTEND SCREEN BACKLOG (Release 1)

Grounded against the verified per-domain audits, the four MediCore reference screenshots, and a direct read of `D:\asthetic2\app\web` (24 page components, 23 authenticated routes + `/login`, 13,741 LOC of pages, 1,633 LOC of shared infrastructure, zero chart dependencies).

## 0. THE HONEST GAP, STATED FIRST

**The reference is not a restyle of the current app. It is a different product tier, and roughly 60% of it is blocked on the database, not on React.**

Three separate gaps are stacked on top of each other, and they must be named separately or the estimate will be wrong:

| Gap | What it is | Can a frontend dev close it alone? |
|---|---|---|
| **1. Visual/system gap** | Stock MUI with a teal/gold theme (`app/web/src/theme/tokens.ts`), no chart library, no stat-card primitive, no wizard, no responsive shell (`AppShell.tsx:77` is `variant="permanent"` at a hard 248px, no breakpoint). Reference is a dense analytics design system: donuts, funnels, progress meters, delta chips, icon strips, paginated tables. | **Yes** — ~4–6 weeks for the primitive layer. |
| **2. Screen-coverage gap** | 23 routes exist. The reference implies ~105 screens for a complete Release 1. Six fully-built, guarded, module-registered backends have **zero UI consumers**: appointments, media/photos, imaging, org-hierarchy (branches/departments/memberships), packs, service-catalog writes. | **Mostly yes** for the six orphaned backends. **No** for the rest. |
| **3. Data-model gap** | The screens the owner most wants cannot be built at any price today. There is no `Room`, no `Expense`, no `Campaign`, no `Commission`/`RevenueShareLedger`, no `Attendance*`, no `FormTemplate`, no `ClinicalRule`, no discount column, no tax column. `Invoice` has no `providerId`. `InvoiceLineItem` has no `serviceCatalogItemId` or `performedById`. **`branchId` exists on exactly 2 of 85 tenant-scoped models** (`Department`, `UserMembership`) and on **zero** transactional tables. | **No.** Schema + service work first. |

**The single most damaging artifact in the repo is `frontend/screens/` — 108 static HTML files** including `appt-calendar.html`, `attendance.html`, `revshare-config.html`, `cp-mrr.html`, `inventory-alerts.html`, `dashboard-doctor.html`, plus `docs/admin-dashboard-mockup.html` (652 lines). They contain **zero fetch/axios/XHR calls**. They are almost certainly the origin of the reference screenshots. **Nothing in `frontend/screens/` may ever be counted as delivered.** Recommend moving the whole directory to `design/mockups/` with a README stating it is non-functional, before anyone reports progress from a screenshot.

**Scorecard against the four reference screenshots:**

| Reference | Current equivalent | Coverage |
|---|---|---|
| 1. Platform Super Admin dashboard | `TenantsPage.tsx` — one table, 6 columns, no pagination. `platformNavGroup` has exactly **one** nav item (`nav.ts:97-102`). Platform admins are hard-redirected past any dashboard (`DashboardPage.tsx:27`). | **~8%** |

| 4. Clinic operations dashboard (9 tiles) | `DashboardPage.tsx` — 4 stat cards + 2 key-value panels, all-time totals, no charts. **7 of 9 tiles are model-blocked.** And it renders a red 403 alert for 5 of 8 roles and for the entire SOLO edition (`reports.controller.ts:11-13` vs `editions.ts:55-63,124`). | **~10%** |

Every one of these is currently absent. Building screens before these exist is how you get 20 hand-rolled charts and 20 bespoke tables. **This layer is the critical path.**

## 3. NEEDS-UPGRADE — SPECIFIC DEFICIENCIES

### A4 — Platform clinics table (`TenantsPage.tsx`)
1. **Patients and Users columns are structurally always 0.** `platform-tenants.service.ts:56-59` calls `patient.groupBy` and `user.groupBy` on the **base** Prisma client outside `forTenant`. `app.tenant_id` is unset (NULL) or reset to `''` at commit of a prior local `set_config`; under FORCE RLS both make the qual evaluate NULL → zero rows. `TenantsPage.tsx:264-265` renders those zeros as real per-clinic counts. **This is a live defect, not a missing feature.** Nothing catches it — `TenantsPage.test.tsx` mocks the response and `tenant_onboarding_suite.py:88` never inspects the payload.
2. No pagination — `TenantsPage.tsx:250` renders every row; the service does an unbounded `findMany` + two full-table `groupBy`s on every page load.
3. No search, no sort, no row click-through (rows are not clickable), no drill-in.
4. Missing columns vs reference: specialty chips, per-module icon strip, MRR, owner, created-by, last activity.
5. No row actions (suspend/resume/deactivate/change plan) — none of those endpoints exist.

### A6 — Clinic onboarding (`TenantsPage.tsx:136-228`)
Single flat `<Dialog>` with 8 fields. Missing **all six reference steps** and every field below:
- Organization name (currently hardcoded `` `${dto.name} Organization` ``), and **no way to attach to an existing organization** — `CreateTenantDto` has no `organizationId`, so every onboarding mints a fresh Organization and the N:1 capacity of `OrganizationClinic` is unreachable.
- Clinic phone, email, addressLine1/2, region, postalCode, country (Branch **has** these columns; onboarding writes only name/code/city).
- Number of branches — always exactly one, code `MAIN`.
- Subscription package — derived from edition by a `findFirst`, never chosen.
- Enabled modules — derived wholesale from the edition bundle; no per-module toggle exists anywhere in the product.
- Subscription **start** date — `Subscription` has no `startsAt` column at all.
- Subscription **expiry** — hardcoded `now + 1 month`.
- No review step, no live summary sidebar, no estimated monthly subscription.
⚠️ Widening this wizard widens an already-uncomfortable transaction window: `Tenant` is created **outside** the provisioning transaction and compensated by a delete (`platform-tenants.service.ts:126-153`).

### C1 — Clinic ops dashboard (`DashboardPage.tsx`)
1. **It renders a red error alert, not a dashboard, for most users.** It is the index route for every non-platform-admin, and its only fetch is `/reports/summary`, which carries `@Roles(OWNER, ADMIN, FINANCE)` **and** `@RequiresEntitlement('reporting.core')`. RECEPTION, DOCTOR, SALES, TREATMENT and INVENTORY — 5 of 8 tenant roles — get 403. SOLO edition grants only CORE, and CORE does not include `reporting.core`, so **a SOLO clinic's own OWNER also lands on a broken page.** Fix before anything else: role-appropriate default landing + a fallback dashboard.
2. All-time totals only. No date range, no period-over-period delta, no comparison.
3. No charts of any kind.
4. 7 of the 9 reference tiles absent: today's appointments (no UI for appointments at all), sessions-in-progress-by-room (no `Room` model), recent consultations (no clinic-wide feed endpoint), revenue-vs-doctor-share donut (no commission model, no chart kit), low-stock consumables (no reorder level, no consumables), doctor earnings (no `Invoice.providerId`), patient queue (no queue model). Only lead funnel exists — and it lives on the CRM page as chips.
5. 9 tiles will mean 9 uncoordinated round-trips without a `GET /dashboard/ops` aggregate.

Missing and required by the brief: email, whatsappNumber, CNIC/identification, addressLine1/2, city, region, postalCode, country, emergencyContact{Name,Phone,Relation}, bloodGroup, maritalStatus, occupation, nationality, preferredLanguage, referralSource, notes, status, updatedAt, deletedAt, branchId, primaryDoctorId, marketingOptIn. **Three things that would make this go badly wrong:**

1. **Building screens before primitives.** With ~105 screens and no `EntityTable`, no chart kit and no `WizardShell`, the codebase gets 30 divergent tables and 20 hand-rolled charts. The primitive layer is not polish; it is the schedule.

2. **Treating the reference screenshots as a UI task.** Screenshot 3's commission-rule card and screenshot 4's room-progress tiles are not CSS — they are `CommissionScheme` and `Room`, neither of which exists among 94 Prisma models. Any estimate that reads those screenshots as design work will be wrong by an order of magnitude.

3. **Deferring `branchId`.** It gets strictly more expensive every day real clinical and financial data accumulates, and a backfill that guesses a branch for historical invoices manufactures financial history. If a multi-branch customer is anywhere on the roadmap, BE1 should be scheduled earlier than Phase 6, accepting the schedule hit.

**Two things that are genuinely strong and should not be rewritten:** the tenant-isolation layer (86 tables under FORCE RLS, boot refusal on a bypassing role, three CI guards that verify from the runtime role rather than self-attesting), and the specialty clinical screens (13 routes, careful engines, real vitest coverage). The plan above adds to both; it replaces neither.

**One pattern to copy everywhere:** `TrendsPage.tsx` + `TrendChartDefinition` is the only complete config-driven chain in the product — manifest → seeded tenant row → API → generic renderer with no per-chart code. It is the working proof that Layer-2 configuration can reach a real screen. `FormRenderer` (P16) and the consultation workspace (C19) should be built to exactly that shape.
