## PHASE 1 — The Branch Dimension (4 weeks) ⚠️ THE 3× TRAP

**Goal:** every operational row knows which branch it happened at, and the branch travels from JWT → context → query → RLS.

**Why now, and why it cannot wait:** this is the single most expensive item to defer. Every sprint you ship without it adds more branch-unaware rows and more write paths to retrofit, and the backfill of historical data *manufactures financial history*. It also blocks, directly: branch reports, branch commission, per-branch stock (a two-branch clinic today would show stock at a site that doesn't have it), per-branch price lists, per-branch attendance, and every acceptance criterion in the plan doc's Phase D.

**Order within the phase matters — get it wrong and you get scattered 500s in unrelated modules:**

1. **Context first.** `tenant.middleware.ts:54-59` currently *discards* `organizationId/clinicId/branchId/departmentId/membershipId` that `switchContext` carefully signs. Extend `TenantCtx` (`common/tenant/tenant-context.ts:19-27`) to carry them. Add `PrismaService.forCurrentBranch()`.
2. **Columns nullable + app-level population.** Add `branchId @db.Uuid` (and `departmentId` where clinically meaningful) to the ~28 tables listed below, each with a composite index `[tenantId, branchId]`. Services stamp it from context on write.
3. **Backfill** to each tenant's `MAIN` branch (reuse `scripts/backfill-phase-a.ts`).
4. **RLS policies last, then NOT NULL.** RLS policies with no `WITH CHECK` reuse their `USING` expression as the INSERT check (documented at `platform-tenants.service.ts:22-26`) — a branch-aware policy added before every write path sets the branch GUC will start rejecting writes from unrelated modules.

**Tables (first wave, in this order — inventory first, because it is where the gap does clinical rather than cosmetic damage):**
`StockItem`, `Dispense`, `DispenseItem`, `DispenseItemBatch`, `VaccineBatch` → `Invoice`, `InvoiceLineItem`, `Payment`, `Refund`, `PaymentIntent` → `Patient`(registeringBranchId), `Appointment`(+departmentId), `Encounter`(+departmentId), `TreatmentPlan` → `Employee`(+departmentId), `PayrollRun`, `Payslip` → `Lead`, `LeadActivity` → `LabOrder`, `ImagingOrder`, `PhotoSession`, `ConsentRecord`, `AuditLog`, `ServiceCatalogItem`(nullable = all branches), `Admission`, `Ward`, `Bed`.

**Also in this phase:** retire `Facility`. It duplicates `Branch`, has `facilityId` on zero models, and is read in exactly one place (`org-hierarchy.service.ts:226`). Two location concepts means every future feature guesses which one is the location.

**Duration:** 4 weeks. Roughly 2 weeks of migration + backfill, 2 weeks chasing write paths.

**Hard acceptance test:** a new `app/backend/test/safety/branch_isolation_suite.py` that (a) creates two branches in one tenant, (b) receives stock at Branch A, (c) authenticates a user whose membership is Branch B, (d) asserts `GET /pharmacy/stock` returns **zero** rows and a dispense attempt against the Branch A batch is **refused**, (e) asserts an invoice raised under Branch B context carries `branchId = B` on the invoice *and* every line item. Extend `scripts/check-rls-coverage.ts` to fail the build if any new tenant-scoped model lacks `branchId`.

## PHASE 2 — Identity, Access & Audit (5 weeks)

**Goal:** a clinic can create, assign, and offboard staff; every privileged action leaves a trace; multi-clinic ownership becomes constructible.

**Why now:** everything downstream needs a person to attribute work to. Commission needs a staff member. Appointments need a validated provider. The membership API built in Phase A has no `userId` to point at, because **there is no users controller anywhere in the backend** — the only `User` a live deployment can hold is the single owner minted at onboarding (`platform-tenants.service.ts:189`). Six of the eight tenant roles can never be held by a person.

**Build:**

**2a. User management (2 wks).** New `UsersModule`: `GET/POST /org/users`, `PATCH /org/users/:id`, `POST /org/users/:id/deactivate`, `POST /org/users/:id/reset-password`, `POST /auth/change-password`, `POST /auth/accept-invite`. New `UserInvitation` table. New columns on `User`: `branchId`, `departmentId`, `phone`, `employeeId` (FK → Employee — join the two identity populations *now*), `lastLoginAt`, `mustChangePassword`, `deactivatedAt`, `tokenVersion`. Check `tokenVersion` in `jwt.strategy.ts:53` — today there is **no token revocation of any kind**, so a departed employee's token works forever.

**2b. Membership lifecycle + cross-clinic (1 wk).** `PATCH`/`DELETE` on `/org/hierarchy/memberships/:id`. Today `POST` silently returns the *existing* row with the *old* role when one matches (`org-hierarchy.service.ts:134-146`) — an admin correcting a role gets HTTP 201 and no change. Add a cross-tenant membership writer (`SECURITY DEFINER`, org-scoped) and accept `organizationId` in `CreateTenantDto` so a second clinic attaches to an existing organization instead of minting a new one. **Also fix the contradiction this exposes:** `User.tenantId` is a scalar with a tenantId-keyed RLS policy (`rls-user.sql:39-42`), so the moment a genuine cross-tenant membership exists, `GET /org/hierarchy/summary` throws `Field user is required, got null`. Make `User.tenantId` the *home* tenant only and relax the User policy to `tenantId = current OR EXISTS(membership in current)`.

**2c. Wire AuditLog (0.5 wk).** `AuditLog` (`schema.prisma:1190`) has **zero writes and zero reads in the entire backend**. Add `actorRole`, `branchId`, `membershipId`, `ip`, `userAgent`, `beforeJson`, `afterJson`. Write via a Nest interceptor, not scattered calls. Every privileged mutation: onboard, suspend, role grant, context switch, refund, void, discount, payroll finalize.

**2d. Tenant lifecycle (0.5 wk).** `Tenant.status` is written once as ACTIVE and **read nowhere** — a suspended clinic keeps working. Add suspend/resume/deactivate endpoints and a `TenantStatusGuard` that rejects a non-ACTIVE tenant. Decide precedence between `TenantStatus`, `OrganizationStatus` and `SubscriptionStatus` **before** writing any of it; today all three are write-only.

**2e. Screens (1 wk).** `/org/staff` (directory + invite + deactivate), `/org/branches`, `/org/departments`, `/org/settings`. This finally gives the Phase A hierarchy API a consumer — right now `grep 'org/hierarchy' app/web/src` returns zero.

**Explicitly NOT in this phase:** the `Role`/`Permission`/`RolePermission` matrix and its editor UI. Ship a fixed, hardened set of role→action mappings in code. The permission table is Phase 5.

**Hard acceptance test:** from a clean seed, using **only the UI**: invite a DOCTOR, accept the invite, log in as them, get refused on `/hr/payroll`, have the OWNER deactivate them, and confirm their **existing token** is rejected on the next request. Separately: create a second clinic under the same organization, grant the owner a membership in it, switch context, and assert clinic A's patients are **invisible** — and that the switch wrote an AuditLog row naming both contexts.

## PHASE 3 — Front Desk & Consultation (6 weeks) — the release-1 heart

**Goal:** a Lahore aesthetics clinic can run a full day in the product: book, check in, consult, record, charge.

**Why now:** these are the two largest holes in the shipped product and they are both *screens over working backends*.
- `grep -ri appointment app/web/src` returns **one hit — a code comment**. The appointments API is complete, guarded, and registered; `appointments.core` is bundled into every edition; there is no calendar, no route, no nav item. Every clinic is sold scheduling and cannot schedule.
- The entire EMR write path (encounters, intake, notes, treatment plans) is reachable **only** from `app/backend/public/aesthetic-workspace.html` — a legacy static demo outside the router, outside entitlements, hardcoded to `packKey: 'aesthetic'`. The shipped React SPA never POSTs a consultation. **The demo is more complete than the product**, which is precisely how work gets reported as done.

**Build:**

**3a. Patient record completeness (1 wk).** `Patient` is 8 columns. Add the ~20 the brief names: `email`, `whatsappNumber`, `identificationType/Number` (CNIC — a Pakistan-first product with no national ID on the patient record), `addressLine1/2`, `city`, `region`, `postalCode`, `emergencyContactName/Phone/Relation`, `bloodGroup`, `referralSource`, `preferredLanguage`, `marketingOptIn`, `status`, `updatedAt`, `deletedAt`, `primaryDoctorId`. Partial unique index on `(tenantId, identificationNumber)`. Refactor `patients.service.ts:50-57` which enumerates fields one by one — every new column currently needs three edits. Add the patient *edit* screen: `PATCH /patients/:id` exists today with **no consumer**, so a typo at registration is permanent.
Add structured `PatientAllergy` / `PatientMedication` / `PatientProblem` with a red allergy banner in the chart header. Today allergies are a free-text key inside one pack's intake JSON — for an injectables clinic that is a safety gap.

**3b. Appointments + rooms (2.5 wks).** `Room` model (there is **no room concept in 94 models**; an aesthetics clinic books laser bays). Add to `Appointment`: `roomId`, `checkedInAt`, `startedAt`, `completedAt`, `checkedOutAt`, `cancelledAt/ById/Reason`, `noShowMarkedAt`, `source` (WALK_IN|PHONE|ONLINE|WHATSAPP|REFERRAL), `bookedById`, `rescheduledFromId`, `serviceCatalogItemId`, `updatedAt`. Add `ProviderSchedule` + `ScheduleException` + `ClinicHoliday`. Add filtering to `GET /appointments` (today it returns *every appointment ever*, unfiltered and unpaginated). Add a `PLAN_TRANSITIONS`-style state machine — `updateStatus` (`appointments.service.ts:57-63`) currently moves COMPLETED back to BOOKED. Add the `ensurePatient`/`ensureProvider` guard the other 8 services use and this one skips.
**Double-booking must be a Postgres `EXCLUDE` constraint over `tstzrange` on `(providerId, [start,end))` filtered to non-cancelled — a read-then-write check in the service is not an acceptable fix.** This is the same TOCTOU shape already fixed for MRNs and lead conversion.
Screens: `/appointments` (day/week, provider columns, room columns), booking dialog with catalogue picker, front-desk day sheet, `/queue` token board.

**3c. Generic form renderer + consultation screen (2.5 wks).** ⚠️ **This is the item most likely to be mis-scoped.** Build `<FormRenderer schema value onChange />` and `<FormViewer />` in the SPA, consuming the *existing* pack config (`GET /intake-groups`, `/note-templates`, `/order-sets`) — port the working renderer at `aesthetic-workspace.html:169-181`. Then `/consultation/:encounterId`: intake + note + orders + plan + follow-up, rendered from the manifest.
Add **server-side validation** of `IntakeSubmission.answers` and `NoteInstance.data` against the template schema — today `required: true` in the manifest is enforced *nowhere* (`emr.service.ts:108-125` writes raw JSON through) and `templateId` is never checked against `templateKey` or the tenant. Stamp `formVersionId` on every submission or old notes become unrenderable the day a form changes.
Add **sign-and-lock**: `signedById`/`signedAt`/`lockedAt` on `Encounter`, `NoteInstance`, `TreatmentPlan`, plus `NoteAmendment` (new rows, never deltas). Today signature exists on exactly one model — `EyeExam` (`schema.prisma:2355-2356`). Without this the clinical record has no medico-legal standing, and every row written before it lands is permanently unattributable.
Add `Encounter.followUpDate` and an `EncounterDiagnosis` child table.
Add `PatientDocument` (ID scans, referral letters) — the only binary store today is `PhotoAsset`, gated behind photography consent.
Delete `app/backend/public/aesthetic-workspace.html` and `pediatrics-workspace.html` when this lands. They are an active reporting hazard and are linked from the backend index page alongside login credentials.

**3d. Pagination (0.5 wk).** `GET /patients` has no `take/skip` and **twelve screens fetch the full list** into dropdowns. At a few thousand patients you ship the entire PHI table on nearly every page view — a data-minimisation problem as much as a scaling one. Add `?q=&take=&cursor=` with a trigram index and a `/patients/lookup` typeahead.

**Hard acceptance test:** one uninterrupted UI session, no curl, no SQL: register a walk-in patient with CNIC and allergy → book them into a room with a provider → attempt a conflicting booking and be **refused by the database** → check in → open the consultation, fill a pack-defined form with a required field left blank and be **refused by the server** → complete it, sign it → attempt to edit the signed note and be refused → raise an invoice from the plan → confirm the chart shows the visit date, the invoice number and the amount **correctly populated**.

## PHASE 4 — Money That Adds Up (8 weeks)

**Goal:** the clinic can price, discount, tax, package, collect, refund, attribute and pay commission — and the numbers reconcile.

**Why now:** it depends on branch (P1), staff identity (P2) and the catalogue picker (P3), and everything after it depends on the ledger. Do not build reporting first; you will report wrong numbers convincingly.

**4a. Catalogue becomes real (1.5 wks).** `ServiceCatalogItem` has 12 columns and **no write API of any kind** — the only writer in the entire backend is the pack seeder, which *overwrites* name/category/price on every re-activation (`pack-seeding.ts:39-46`). Add a `source` discriminator (PACK|TENANT|OVERRIDE) **before** shipping the editor or a routine pack upgrade silently reverts every clinic's prices. Add: `serviceType` enum, `specialty`, `taxRatePct`, `taxCode`, `sessionsIncluded`, `sessionIntervalDays`, `followUpAfterDays`, `requiredConsentScope`, `pre/postInstructions`, `commissionSchemeId`, `roomTypeId`, `branchId`, `effectiveFrom/To`. Screens: catalogue list + editor + price history.

**4b. Two columns that unblock four features (0.5 wk — do this first, it is tiny and everything waits on it).**
`InvoiceLineItem.serviceCatalogItemId` and `InvoiceLineItem.performedById`. The DTO already *accepts* `serviceCatalogItemId` (`create-invoice.dto.ts:21`) and `buildLines` silently **discards** it (`billing.service.ts:449-473`) — the API contract currently lies. `TreatmentPlanItem` persists it and conversion destroys it. Meanwhile `BillingPage.tsx:319` mints synthetic `SVC-N` codes that match no catalogue row, so even after-the-fact reconciliation is impossible.
**Every invoice raised between today and this migration is permanently unattributable to a service or a doctor.** Per-service revenue, commission, package decrement and price-variance all wait on these two columns.

**4c. Invoice restructure — tax and discount (1.5 wks).** `Invoice.total` is one undifferentiated `Int`. Decompose into `subtotalPkr`, `discountPkr`, `taxPkr`, `total`; on the line add `listPricePkr`, `discountPkr`, `discountReason`, `discountApprovedById`, `taxRatePct`, `taxAmountPkr`, `hsCode`. Price server-side **from the catalogue**, not from the request body — today any FINANCE or RECEPTION token can bill any amount and nothing records that it differed from list.
Move FBR identity off process-global env (`fbr.service.ts:39`): a new `TenantTaxProfile` (per branch — FBR POS IDs are issued per point of sale). **Today every tenant on the box would file under one NTN, with `TaxRate: 0` and `PCTCode '0000.0000'` hardcoded** (`fbr.service.ts:157-158`). That is not a stub, it is a materially incorrect filing waiting for credentials. Keep the transport stubbed; fix the payload and the identity now.

**4d. Patient ledger (1.5 wks).** Append-only `PatientLedgerEntry` (CHARGE|PAYMENT|REFUND|CREDIT|ADJUSTMENT|WRITE_OFF) + `PatientAccount`, written by every money-moving path inside the same transaction — including pharmacy, which today is a **completely separate money system** with its own receipt series that never appears in the billing view. Then: advances (make `Payment.invoiceId` nullable — advances are currently impossible at *schema* level), credit balances, `PaymentAllocation`, installment plans. Screens: patient statement (printable), invoice register, cashier day-book, aged receivables. Today `billing.controller.ts` offers only per-patient list and get-by-id — there is no way to see today's invoices or who owes money.

**4e. Packages & sessions (1.5 wks).** `ServicePackage`, `ServicePackageItem`, `PatientPackage`, `PatientPackageSession`. Buy 6 laser sessions, redeem one per visit, with expiry and per-redemption audit; recognise revenue on redemption. The flagship aesthetic manifest **advertises packages in its own description** (`aesthetic.manifest.ts:17`) and its catalogue contains none. For this client this is the single most commercially important missing feature.

**4f. Commissions (2 wks).** `CommissionScheme` (all 7 bases the brief names), `StaffCommissionAssignment`, **`CommissionEarning` as an immutable ledger keyed to individual `Payment` and `Refund` rows — never a recomputation over `Invoice.paid`.** `Invoice.paid` is a mutable running total that a refund *decreases*, and the refund path deliberately collapses a refunded invoice to be byte-identical to a never-paid one (`billing.service.ts:251-258`). Recompute-on-read means paying commission on money the clinic returned, with no clawback and no trace. Decide the rounding policy (whole-rupee ints truncate every percentage) and post the residual explicitly. Recognise on **collection**, not on invoice. Feed into `PayslipComponent`.

**4g. Payslip becomes a component table (0.5 wk).** `Payslip` has 4 numeric columns against the brief's 12. Do **not** add eight more `Int` columns — add `PayslipComponent (type, label, sign, amountPkr, sourceRef)`. Also persist the deduction `reason` that the DTO validates and then silently throws away (`run-payroll.dto.ts:23-26` vs `hr.service.ts:99-109`) — every deduction on every finalized payslip is currently unexplained.

**4h. Expenses & P&L (1 wk).** `ExpenseCategory`, `Expense`, `Vendor`. There is no expense model among 94, so "net profit" is not unbuilt — it is uncomputable. Note also that `reports.service.ts:99` returns collections-minus-refunds under the name `netRevenuePkr`; **rename it to `collectionsNetOfRefundsPkr` while there is exactly one consumer.**

**Hard acceptance test:** sell a 6-session package with a 10% approved discount and 5% tax to a patient who pays half as an advance and half on session 3; redeem 3 sessions across two branches; refund session 3. Then assert: the patient statement's closing balance equals the ledger sum; per-service revenue attributes to the right catalogue item and performer; the doctor's commission ledger shows a **negative reversal entry** for the refunded session; branch A and branch B revenue reports sum to the tenant total; and the FBR payload carries the tenant's own NTN and a non-zero tax rate.

## PHASE 5 — Configuration Engine (8 weeks) ⚠️ THE SECOND 3× TRAP

**Goal:** specialty #2 is a manifest, not a rebuild. Rules are data.

**Why here and not earlier:** the brief's central principle — "do not hard-code separate applications per specialty" — is **not met**: 30 specialty-specific Prisma tables, 47 of 74 enums, 7 bespoke NestJS modules, 9 hand-written React pages. Ophthalmology cost 216 lines of schema, 24 RLS statements, 618 LOC of TypeScript, a 359-LOC React page and edits to four frontend files. That is the true cost of specialty #2 today.

**But the trap is dormant if you freeze specialty work.** So: **hard rule — no new specialty pack ships before Phase 5 completes.** If sales needs specialty #2 sooner, that is the trigger to pull Phase 5 forward, not to hand-code it "just this once."

**Build:** `FormTemplate` / `FormTemplateVersion` / `FormFieldRegistry` / `FormTemplateBinding` (by branch, department, provider, encounter type) with a draft/publish/archive lifecycle and **copy-on-edit** so pack re-activation cannot wipe a clinic's customisation. Extend the field-type vocabulary from 7 to ~18 — the brief explicitly names **image, file upload, digital signature and conditional logic**, none of which exist. Add `SignatureCapture`. Add a conditional-visibility AST evaluated identically client and server. Then `ClinicalRule` + `RuleExecutionLog` + `RuleOverride`, and migrate the hard-coded engines onto it.

⚠️ **Safety constraint on the rules migration, non-negotiable:** `dermatology/engines/phototherapy.engine.ts:15-47` documents *three successive generations* of that engine producing more UV for a worse reaction, all caused by rule-ordering and early-return semantics. A generic first-match-wins evaluator would reintroduce those bugs across every specialty at once. The generic engine's contract must be **"every applicable rule contributes a candidate, most conservative wins, single clamp at a single exit"**, and the dermatology safety suite must pass against the generic path *before* the hard-coded one is deleted.

Also here: make `PackVersion` genuinely immutable (both write paths currently `upsert` with `update: { manifest }`, so a reboot silently rewrites an activated version's manifest), allow version pinning and rollback, wire `manifest.instruments` and `manifest.widgets` (both declared and read by nothing), drive nav from activated packs instead of the hardcoded array in `nav.ts`, and validate `requiresEntitlements` at publish time.

**Hard acceptance test:** onboard a fictional "Trichology" clinic and deliver a working intake form, note template, service catalogue, a dose-limit rule and a nav entry **with zero commits to `app/backend/src` or `app/web/src`** — manifest and admin UI only. Then publish a v2 of the aesthetic pack and prove a clinic's edited consent form survives the upgrade.

## PHASE 6 — Reports, CRM & WhatsApp (6 weeks)

**Goal:** the owner can see the business; the clinic can talk to patients.

**Why last:** every report is a lie until the underlying columns exist. Building the report centre before Phase 4 means twenty bespoke queries that all have to be rewritten.

**6a. Report engine (2.5 wks).** Introduce a **report-descriptor layer** (id, title, required entitlement, parameter schema, column schema) before writing report #3 — otherwise 20 reports become 20 bespoke controllers and 20 bespoke pages. Every route takes `from/to/branchId/groupBy`. **Today `GET /reports/summary` and `/reports/revenue` accept no parameters at all — every number in the product is an all-time scalar**, and 13 unbounded aggregates run on every dashboard load. Add CSV export. Adopt one chart library (there is currently none; the only charts are two hand-rolled clinical SVGs). Deliver: revenue, payments, outstanding+aging, appointments, visits, new/returning patients, services sold, expenses, P&L, doctor performance, staff performance, inventory consumption, low stock, expiring stock, payroll, CRM conversions, **branch comparison**.

**6b. Per-tenant integration credentials (1 wk) — blocker for anything WhatsApp.** `whatsapp.service.ts:40-48` captures config in a **singleton constructor** from process-global env. The instant a real Meta credential is configured, **every tenant on the deployment sends from one clinic's WhatsApp number.** Build `IntegrationConnection` (per tenant, secret by reference), make the service take a resolved connection, and split `integrations.core` into `whatsapp.core` / `fbr.core` / `telehealth.core` — today the CLINIC edition gets `crm.core` without `integrations.core`, so the mainstream edition has a CRM that structurally cannot send a message.

**6c. Message log + templates (1.5 wks).** `MessageThread` / `Message` / `MessageStatusEvent`, unique on `(tenantId, channel, externalMessageId)`. **Today a sent message writes nothing — not even an AuditLog row**, and the value of this table is retroactive: you cannot reconstruct January's sends in March. Add `WhatsAppTemplate` with approval status synced from Meta. Add a `MARKETING` consent scope (`ConsentRecord.patientId` is NOT NULL, so a *lead* cannot hold consent at all) and gate marketing sends on it. Add `SALES` to the roles allowed to send — the one role whose job is working leads over WhatsApp is currently locked out (`FRONT_DESK_ROLES`).

**6d. Scheduler (1 wk) — there is none.** Zero `@Cron`, `ScheduleModule`, BullMQ or `setInterval` anywhere in the backend. Appointment reminders, payment reminders, follow-up messages, webhook retries and subscription expiry all need it. Pick the primitive once (BullMQ+Redis, or `@nestjs/schedule` + a claim-locked `MessageOutbox`) and build it deliberately, not under deadline for whichever feature needs it first.

**6e. CRM completion (1 wk).** Pipeline stages 5 → 8 (as a `LeadStage` table, not a Prisma enum), guarded transitions (today `PATCH status=CONVERTED` sets the terminal state with a NULL patient and **permanently bricks the real convert path**), `LeadLostReason`, `LeadSource`+`MarketingCampaign` (replace the free-text `source`), real assignment (`assignedToId` today is a bare column with no FK, no writer, no reader), ownership scoping, dedupe on E.164 phone, lead detail + follow-up worklist screens (4 of 9 CRM routes currently have no caller). Meta Lead Ads webhook ingestion — note this needs a genuinely **new unauthenticated auth path** (every controller assumes JWT + TenantMiddleware; tenant must be resolved from `pageId`/`phoneNumberId`), with HMAC verification, raw-payload-before-parse, and `unique(source, externalEventId)` because Meta retries for ~36h.

**Hard acceptance test:** two tenants, each with its own WhatsApp connection, send a template message; assert each send used its own `phoneNumberId`, wrote a `Message` row linked to the lead, and was **refused** for a lead without marketing consent. Separately: run the branch-comparison report for a defined month across two branches and reconcile every figure against the ledger by hand.

## CUT FROM RELEASE 1 — and why that is safe

| Cut | Why safe |
|---|---|
| **Insurance / corporate / panel billing** (Payer, Claim, PayerTariff, PreAuth — XL) | The first client is a self-pay Lahore aesthetics clinic. Zero payers. Building an XL claims subsystem for a market segment you have not sold to is the worst ROI in the backlog. |
| **Camera attendance hardware** | No vendor selected, no device, no API. Ship `AttendanceEvent` + a manual-punch UI + a provider interface seam so the hardware plugs in later without redesign. Do not fabricate a device integration. |
| **Patient portal / public online booking** | An entire second product surface with its own identity model. Book last, after the internal calendar, availability and conflict prevention exist — otherwise you expose an unreliable calendar to the public. |
| **Cross-tenant consolidated org dashboard** | The first client has one clinic. It is also architecturally hostile: the `Organization` RLS policy (`rls.sql:614-622`) makes org rows invisible from inside a tenant, so this needs either a bespoke SECURITY DEFINER aggregate or an N-pass loop. Build per-branch reporting (Phase 6) which the client actually needs; build cross-clinic when a second clinic exists. |
| **Role/Permission matrix editor UI** | Ship hardened role→action mappings in code (Phase 2), permission tables in Phase 5. A configurable permission UI over a system with no audit log and no ownership scoping is a lockout generator. |
| **Purchase orders, suppliers, stock transfers, cycle counts** | Real gaps, but a single-branch clinic buys fillers on invoice. Ship the item master + movement ledger (which everything else needs) and defer procurement to R1.5. **Do not defer the movement ledger** — `quantityOnHand` is mutated in place with no history, and every later inventory feature is blocked on that refactor. |
| **Live FBR filing** | Keep the transport stubbed. But fix the per-tenant NTN and the real tax rate in Phase 4 — those are app-data defects, not credential defects, and going live with `TaxRate: 0` files incorrect returns. |
| **Telehealth, IPD/wards/beds, obstetrics, ophthalmology, dental, rehab, immunization, paediatric dosing** | Already built to varying degrees. **Freeze them.** No new investment, no new specialty pages, until Phase 5 makes specialties configuration. Every hour spent hand-coding a specialty screen before the form engine is an hour spent building something you will delete. |
| **`/v1` namespace migration** | Formally abandoned. Version at the edge later if needed. |

## ORDERING TRAPS — the things that cost 3× if done out of order

1. **`branchId` before more domain tables and before more production data.** Every day of delay adds rows whose branch must later be *guessed*. The backfill manufactures financial history.
2. **Within Phase 1: context → nullable columns → app population → backfill → RLS policy → NOT NULL.** RLS policies without `WITH CHECK` reuse `USING` as the INSERT check; adding the branch policy first produces scattered 500s in modules nobody touched.
3. **`InvoiceLineItem.serviceCatalogItemId` + `performedById` before ANY revenue reporting or commission work.** Two columns, half a day. Every invoice written before them is permanently unattributable.
4. **Invoice subtotal/discount/tax decomposition before real invoices accumulate.** Retrofitting tax means either backfilling every historical invoice or living with two incompatible invoice eras forever.
5. **The patient ledger before advances, credits, installments and commission.** They all read from it; building them on ad-hoc queries means rewriting all four.
6. **Commission as an append-only ledger keyed to `Payment`/`Refund` rows, never a recomputation over `Invoice.paid`.** `paid` is mutable and a refund decreases it. Recompute-on-read pays commission on returned money with no clawback.
7. **`source`/override discriminator on catalogue and form config before shipping any editor.** `pack-seeding.ts` overwrites unconditionally on every re-activation; ship the editor first and the next pack upgrade silently wipes every clinic's prices and forms.
8. **The form *renderer* (Phase 3) before the form *builder* (Phase 5).** A builder over a read path that no screen consumes ships a UI that edits invisible data.
9. **The form engine before specialty pack #2.** Ophthalmology's true cost was ~1,200 lines across schema, RLS, backend, frontend and four config files. Pay that once more and you have paid for the engine twice over.
10. **`IntegrationConnection` before any real WhatsApp credential touches the box.** The current singleton means one clinic's phone number sends for every tenant — a cross-tenant identity leak and a Meta policy breach on day one.
11. **The message log before the first message is sent.** Its value is retroactive and cannot be backfilled.
12. **User management before membership/RBAC screens.** The membership endpoint has no `userId` to point at until users can be created.
13. **AuditLog wired in the same interceptor as the permission system.** Retrofitting audit afterwards means touching every mutation twice.
14. **Sign-and-lock on clinical notes before the first real clinic goes live.** Every pre-signature row is permanently unattributable; there is no retroactive fix.
15. **Choose the scheduler primitive once, deliberately.** The first time-triggered feature will otherwise design it under deadline pressure, and the next four inherit it.
