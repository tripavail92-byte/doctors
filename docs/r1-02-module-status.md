# HEALTH OS — RELEASE 1 MODULE LEDGER
### Deliverables 3, 4 & 5: what is done, what is broken, what must be built

Scope basis: the Release 1 mandate (1A security/foundation, 1B small-clinic operations, 1C sales/workforce), the acceptance thread `Lead → Appointment → Patient → Consultation → Treatment Plan → Payment → Treatment Session → Inventory Consumption → Doctor/Clinic Share → Report`, and the partner's two binding clarifications (branch columns now / consolidated branch reporting deferred; hybrid specialty without a form builder).

**Every one of the 34 modules in `app/backend/src` is accounted for in exactly one of Tables A, B or C.** Nothing is listed twice, so the day totals add up.

**Customer reality check that shapes all three tables.** The Lahore clinic is provisioned on `Edition.DERMATOLOGY`, which resolves to `CORE + CLINIC_ADDONS + SPECIALTY_SHARED + pack.aesthetic + pack.dermatology` (`app/backend/src/entitlements/editions.ts:88-92, :127`). That bundle **does not contain `hr.core` or `pharmacy.core`**. `filterNav` (`app/web/src/layout/nav.ts:86-95`) therefore renders exactly nine menu items for this customer — Dashboard, Patients, Severity grading, Phototherapy, Trends, Billing, Leads, Reports, Integrations — and `EntitlementGuard` 403s every `/hr/*` and `/pharmacy/*` request. **Two of the three things Release 1 is being built to sell (payroll and consumable inventory) are entitlement-blocked on the only customer.** That is a two-line fix (Table B, row B10) and it must land before 1B/1C work starts, not when it fails.

**Calendar translation, stated plainly.** One developer: ~14 months — not a viable plan. Three developers with 1A as a serial gate: **1A ≈ 10 weeks (mostly one person; it does not parallelise well), then 1B ≈ 10-12 weeks across three, then 1C ≈ 7-8 weeks across two** — call it **27-30 calendar weeks, or roughly 6.5-7 months, to the first clinic opening its doors on this software.** Add 3-4 weeks of integration hardening, data migration rehearsal and on-site setup before that is a date you would say out loud to a customer.

The re-scope did **not** make Release 1 cheap. The old roadmap's 32-37 weeks was optimistic for a much larger scope; this plan is 27-30 weeks for a scope that a clinic can actually run on every day. What the re-scope bought is not speed — it is **finishability**: roughly 200-250 developer-days of work (form builder, rules engine, insurance/claims, multi-branch RLS, platform portal, quotas, roster/shifts, patient portal) moved out of the path to first revenue, and a release whose acceptance criterion is one unbroken thread rather than a feature count.

**Where the ratio is best, in order.** These are the rows to start on Monday: B10 (0.5 days makes payroll and inventory visible to the customer at all), C52+C53 (4 days of pure frontend turns a static lead list into a working follow-up system, no backend, no migration, no tables), C28 (3 days of screen on a complete, consent-gated, entitled photo backend), C14 (3 days that unblocks the consultation screen, custom fields and every future pack), B2+B3 (2 days that prevent the only unrecoverable data loss in the plan), and C44's extraction of the existing FEFO engine (reuses the best-engineered code in the project instead of hand-rolling a second copy of its lock discipline).

**Three rules for reporting progress on this plan.** A static mockup is not progress — `frontend/screens/` holds 108 HTML files with zero network calls and they must never appear in a status update. A Prisma model is not progress. An endpoint with no caller is not progress: six fully-built backends (appointments, media/photos, imaging, org-hierarchy, packs, service-catalog writes) sit in this repository today with zero UI, and they are simultaneously the cheapest wins in the project and the clearest evidence of how "done" has been mis-reported here before.

## DEFERRED TO UNIVERSAL PLATFORM EXPANSION

Everything Release 1 drops, with why it is safe and what it costs later.

### D1 — The form builder (`FormTemplate`, `FormField`, `FormBinding`, designer UI, conditional logic, signature capture) — **SAFE to defer**
`audit-04:896-926` sizes this XL. It is safe because the mandate's actual requirement — "dermatology/aesthetic templates" — **is already met at the data layer**: `aesthetic.manifest.ts:21-105` and `dermatology.manifest.ts:15-52` ship real skin-profile, safety-flag, assessment and injectables templates, seeded per tenant on every onboarding (`pack-seeding.ts:61-93`, `platform-tenants.service.ts:310-339`). Release 1 delivers `PackFormRenderer` (C14) + simple custom fields (C19), which covers the clinic's real need. Later cost: ~30 developer-days, **plus** a copy-on-write migration for pack-seeded templates. That migration is the reason C19 uses a **separate `TenantCustomField` table** rather than letting tenants edit `NoteTemplate.schema` — the seeder overwrites schema on every activation (`pack-seeding.ts:63-79`), so keeping custom fields out of the pack tables means the copy-on-write problem does not have to be solved twice.

### D2 — The generic clinical rules engine (`ClinicalRule`, `RuleExecutionLog`, condition/action builder, simulate, override queue) — **SAFE to defer, and safer deferred than shipped**
`audit-04:928-934, :984`. Every clinical rule today is a compile-time TypeScript constant, and the ones that matter are **correct and adversarially verified** — the phototherapy engine documents three successive generations that produced *more* UV for a *worse* reaction, all caused by rule-ordering and early-return semantics (`dermatology/engines/phototherapy.engine.ts:15-47`). A naive first-match-wins data engine would reintroduce every one of those bugs across every specialty at once. Deferring is not just cheap, it is the clinically safer choice. Later cost: ~30 days, and the generic evaluator **must** adopt "every applicable rule contributes a candidate, most conservative wins, single clamp at a single exit" as its contract, with the derma safety suite re-run against the generic path before the hard-coded one is deleted.

### D3 — Branch-scoped RLS policies, the `app.branch_id` GUC, the `NOT NULL` pass, and all cross-branch/consolidated reporting — **SAFE to defer** (the *reporting*, not the columns)
`audit-01:59-67` costs the full version at 7-9 weeks. With exactly one branch there is no sibling branch to hide, and tenant isolation — the thing that actually protects the customer — is untouched. There is a documented trap: a policy with no explicit `WITH CHECK` reuses its `USING` expression as the insert check, so a branch predicate starts rejecting writes as scattered 500s in unrelated modules. Release 1 keeps `branchId` nullable and enforces non-null in the auto-stamp extension (C10) instead. Saves ~3 weeks. **This is deferring the readers, not the writers — see the asymmetry below.**

### D4 — RBAC v2 (`Role`, `Permission`, `RolePermission`, `MembershipScope`, `@RequiresPermission`, per-action verbs) and deny-by-default across all 207 handlers
Release 1 keeps the 9-value `UserRole` enum plus `@Roles`, and scopes the sweep to the ~10 controllers in the Release 1 flow (B4). Two of the brief's verbs have no operation to permission anyway — there is no export endpoint in any controller, and "discount" appears zero times in the schema until C33 adds it. The six missing brief roles (Org Super Admin, Branch Manager, Nurse, Technician, HR Officer, Payroll Officer) wait for the `Role` table: adding them now means a Prisma enum migration plus hand-edits to five arrays in `rbac/role-groups.ts`. ### D5 — The Platform Super Admin portal beyond the existing list: tenant lifecycle (activate/suspend/deactivate), quotas, subscription lifecycle, module matrix, support access/impersonation, onboarding wizard, organizations CRUD, cross-tenant memberships
`audit-04:127-206`. There is one clinic. `Tenant.status` is written twice and read never; `Subscription.currentPeriodEnd` is written once and read by nothing; there is no `prisma.tenant.update` in the repository. Release 1 fixes only the always-zero counts (B11). Support access is not a controller-shaped gap — a platform admin carries `tenantId=null`, `getTenantId()` throws (`tenant-context.ts:77-78`), and `FORCE` RLS returns nothing, so it needs a scoped-token design plus a new SECURITY DEFINER path. ## THE ASYMMETRY: WHY THE FORM BUILDER IS SAFE TO DEFER AND `branchId` IS NOT

This is the single most important sentence in the plan, so it is stated as plainly as possible.

**The form builder and the rules engine are additive.** They introduce new tables that reference existing rows and change no existing row's meaning. Ship them in month 18 and every note written in month 3 is still valid, still renderable, still queryable. The clinic is not *missing* anything in the meantime — the derma/aesthetic templates already exist as seeded tenant rows, and the clinical engines are correct, verified and safer as code than they would be as data. **The cost of deferring is later effort at the same price.** Nothing is lost by waiting.

**`branchId` is not additive. It is a fact about a row that only exists at the moment the row is written.** Every operational record created without it records a truth that cannot be reconstructed afterwards. In March you cannot determine which branch a January invoice belonged to, which branch consumed that vial of Botox, or which branch's doctor earned that commission. The backfill is not a migration — **it is a guess**: everything becomes MAIN. The day the clinic opens branch #2, every historical row is silently mis-attributed, and revenue-by-branch, stock-by-branch and commission-by-branch are permanently wrong for the entire pre-migration period, with no error message and no way to detect it from the data. **The cost of deferring is not later effort. It is unrecoverable data, and it compounds every day the clinic operates.**

The partner's clarification threads this precisely: **do the column and context work now (cheap: C9 + C10 + B2 + B3 ≈ 9.5 days), skip the cross-branch reporting and scoping features (expensive and risky: ~3 weeks, D3).** The writers are not deferrable. The readers are.

**The same asymmetry applies to five other items in this plan. Each is cheap now and unrecoverable later, and each must land in Release 1 for exactly that reason:**

| Item | Row | Why it is unrecoverable |
|---|---|---|
| `InvoiceLineItem.serviceCatalogItemId` + `performedById`, `Employee.userId` | C29 | "Which doctor earned this revenue" cannot be derived from a line that never recorded a performer. Every invoice written before it is permanently unattributable, and the DTO already accepts and silently discards the field (`create-invoice.dto.ts:19-21` vs `billing.service.ts:449-473`) — so the API is lying about it today. |
| Clinical note `signedById` / `signedAt` / `lockedAt` | C18 | Present on **one model out of 94** (`EyeExam`, `schema.prisma:2355-2356`). Every note written before sign-and-lock ships is permanently unattributable, and the clinical record has no medico-legal standing for that period. A signature cannot be applied retroactively. |
| `StockMovement` ledger | C45 | `quantityOnHand` is mutated in place with no `updatedAt`. "Why is this 43 and not 50" is unanswerable from day one, and the movement history for the pre-ledger period cannot be reconstructed from the balance. |
| Outbound `Message` log | C59 | `whatsapp.service.ts:75-87` persists nothing today — not a Message row, not an AuditLog row. January's sends cannot be reconstructed in March. |
| Lead → Patient attribution (`source`, `interest`, `assignedToId`, `marketingOptIn`) | B20 | `convert()` writes name and phone only (`crm.service.ts:137-139`). "Which salesperson brought this revenue" — the entire basis of 1C sales commission — is discarded at the exact moment it becomes financially load-bearing, and no later query can recover it. |

Everything else on the deferred list can wait. **These six cannot, and the reason is the same in every case: they are not features the clinic will notice missing — they are facts that stop existing the moment they are not written down.**
