_Generated by multi-agent audit against the Universal Clinic SaaS brief._

# Architecture Verdict — Health OS (D:\asthetic2)

## Before anything else: a live privilege-escalation hole

I need to put one thing above the architecture discussion, because it is not a design opinion — it is a working exploit I traced myself, link by link, in this session.

Any clinic OWNER or ADMIN can make themselves a platform super-admin in two HTTP calls and then read and modify every other clinic on your platform.

The chain: `POST /org/hierarchy/memberships` is guarded to OWNER and ADMIN (`app/backend/src/platform/org-hierarchy.controller.ts:11-12`). Its input validator accepts any value of the role enum — `@IsEnum(UserRole)` at `app/backend/src/platform/dto/hierarchy/create-membership.dto.ts:8` — and `PLATFORM_ADMIN` is a member of that enum. The service writes the role verbatim (`org-hierarchy.service.ts:163`), and its only safety check is that the target user belongs to the caller's own clinic, which the caller satisfies trivially by naming themselves. Then `POST /auth/switch-context` mints a fresh token carrying that role: `role: chosen.role, isPlatformAdmin: false` (`auth/auth.service.ts:196-200`). Finally `RolesGuard` decides purely on the role string — `if (!required.includes(user.role as UserRole)) throw` (`rbac/roles.guard.ts:38`) — with no cross-check that a `PLATFORM_ADMIN` role implies the `isPlatformAdmin` claim. `PlatformTenantsController` is guarded by exactly that decorator (`platform-tenants.controller.ts:21-22`), so `GET /platform/tenants` now returns every clinic on the platform, and `POST /platform/tenants` can mint new ones.

Three small fixes close it, and all three are needed because each alone leaves a variant open: reject any token where `role === PLATFORM_ADMIN` but `isPlatformAdmin !== true`; replace the bare enum validation with an explicit allow-list that excludes `PLATFORM_ADMIN` and `OWNER`, enforced again in the service rather than only in the DTO; and refuse to sign a context-switch token whose role exceeds what the underlying `User` row permits. Then add a safety suite that performs the actual four-call exploit and asserts a 403 on the last call. Your existing suite tests this boundary only with a plain OWNER login token (`test/safety/tenant_onboarding_suite.py:88`), which is why it stays green while the hole is open. This is a day of work, and it should happen before any of the architecture work below.

## 1. The four-layer principle: Layer 2 exists, but nothing stands on it

The honest answer is that the team did not skip Layer 2 — they built a real one, and then built Layer 3 beside it instead of on top of it. This is a more subtle failure than "they skipped it," and it matters because the fix is different.

Here are the counts, all verified directly against `app/backend/prisma/schema.prisma` (3,007 lines, 94 models, 74 enums) in this session.

The configuration engine — Layer 2 — is six tenant-scoped tables: `ServiceCatalogItem` (line 1285), `NoteTemplate` (1311), `IntakeFieldGroup` (1329), `OrderSet` (1345), `TrendChartDefinition` (1369) and `DoseRule` (2768), plus four catalog tables that distribute them (`Pack` 1226, `PackVersion` 1241, `InstrumentDefinition` 1256, `PackActivation` 1267).

The specialty verticals — Layer 3 — are thirty hard-coded tables. Obstetrics owns six (`PregnancyEpisode` 1852 through `GynaeProfile` 2046). Dental owns seven (`ToothRecord` 667, `PerioExam` 2154, `PerioToothRecord` 2173, `ToothPlanItem` 2196, `OrthoCase` 2222, `OrthoEvent` 2246, `ToothFinding` 2873). Ophthalmology owns six (`EyeExam` 2348 through `OpticalPrescription` 2453). Rehab owns five (`RehabEpisode` 2505 through `ExercisePrescription` 2602). Dermatology owns three, immunization three.

That is thirty specialty tables against six configuration tables — a five-to-one ratio pointing the wrong way. The enum count tells the same story more sharply: of 74 enums, only about 27 are universal (`InvoiceStatus`, `PaymentMethod`, `AppointmentStatus`, `EncounterStatus` and so on). The other 47 exist to serve six specialties. Obstetrics alone contributes 22 (`EddMethod`, `RhFactor`, `Presentation`, `DipstickResult`, `FhrMethod`, `OedemaGrade`, `LiquorAssessment`, `MembraneStatus`, `PartogramStatus`, `FhrDecel`, `AmnioticFluid`, `CycleRegularity`, `DysmenorrheaSeverity`, `TubalTest` and more). Every one of those is a clinical vocabulary term that lives in the database *type system*, meaning that adding one word to one dropdown requires a schema migration and a redeploy.

The code volume confirms it. Seven specialty backend directories total 8,178 lines (`dental` 1,308, `dermatology` 1,990, `obstetrics` 1,824, `immunization` 1,164, `dosing` 661, `ophthalmology` 618, `rehab` 613). The entire Layer 2 read API — `app/backend/src/catalog/` — is **102 lines**. The pack machinery is real at 1,631 lines, but almost all of it is distribution (validate, publish, version, seed); the part that lets a clinic *use* the config is a hundred lines of read-only controller.

The decisive finding, though, is at the frontend. I grepped the entire React application (`app/web/src`, 24 pages, 23 routes) for calls to `/intake-groups`, `/note-templates`, `/order-sets`, `/service-catalog` and `/packs`. There is exactly one match, and it is `DermatologyGradingPage.tsx:101` calling `/dermatology/instruments` — which is not the configuration engine at all, but a separate hard-coded TypeScript constant served through the dermatology controller.

**The shipped product does not read Layer 2 at any point.** The only consumers of the configuration engine are two legacy static demonstration pages in `app/backend/public/` (`aesthetic-workspace.html`, `pediatrics-workspace.html`) that pre-date the React port. So the pack manifests seed rows into six tables that nothing in the customer-facing application ever displays. Layer 2 is not skipped; it is orphaned.

There is one true exception, and it is important because it proves the design works: the trend chart. `TrendChartDefinition` is authored in a manifest, seeded per tenant (`packs/pack-seeding.ts:116-139`), served by `GET /trends/definitions`, and rendered by a *generic* component (`app/web/src/pages/TrendsPage.tsx:74`) that has no per-chart code. One chart definition, one renderer, any number of charts. That single feature is the working proof of concept for everything else in this section, and the team should be told that clearly — they built the right thing once and then did not repeat it.

So: adding a new specialty today costs what ophthalmology cost. Roughly 216 lines of schema (six models plus ten enums), 24 RLS statements, a NestJS module, nine controller routes, a 359-line hand-written React page, an entry in `App.tsx`, an entry in `nav.ts`, an `Edition` enum value, a feature key — and *then* a manifest. The brief promises configuration-only onboarding. The reality is a core rebuild per specialty.

## 2. The single most consequential decision: the domain tables have no place

If I can change only one thing, it is this: **every operational record in this system is scoped to a tenant and to nothing else.** No invoice, appointment, patient, encounter, stock item, employee, payslip or lead knows which branch it belongs to or which department produced it.

I verified this exhaustively. A grep for `branchId` across the entire 3,007-line schema returns **seven lines**, and all seven live between lines 325 and 367 — the `Department` model and the `UserMembership` model. `departmentId` returns three lines, all in `UserMembership`. Of the 85 tenant-scoped models, **two carry a branch and neither of them holds any business data.**

This is the most consequential decision because it is the one that becomes more expensive every single day. Everything else on this list can be built later at roughly the same cost. This one cannot: it is a change to the shape of rows you are already writing. Every invoice raised between now and the migration is an invoice whose branch has to be *guessed* during backfill. Every dispense, every payslip, every lead. When a two-branch customer eventually asks "how did Gulberg do last month compared to DHA," the answer for all history before the migration will be manufactured, not recorded.

It also blocks a startling amount of the brief at once. Branch revenue, branch attendance, branch stock, branch commission pools, per-branch price lists, branch-level access control for a branch manager, the consolidated-versus-branch dashboard, and the plan document's own Phase A acceptance criterion "branch-scoped data queries enforced" — none of these are separate features waiting to be written. They are all one migration waiting to happen. Phase A shipped the hierarchy tables and the clinic switcher; it did not connect them to a single row of data. Phase A should be recorded as roughly one-third complete, not complete.

There is a second, quieter part of the same decision that will cost real money if it is not made now. Two structural gaps sit alongside the branch gap and share its "must be decided before more rows exist" character. `InvoiceLineItem` (`schema.prisma:597-617`) has no `performedById` — no billed line names the person who earned it. And `Employee` (`schema.prisma:859-882`) has no `userId` — the doctor who performed a procedure is a `User`, the person payroll pays is an `Employee`, and there is no join between them. Together these mean doctor performance, doctor share, commission and revenue split are not merely unbuilt reports; they are *unrecoverable from historical data*. The P&L-by-doctor will have a hole exactly the size of the delay before these columns land.

### What the migration actually costs, concretely

This is not a schema change. It is a four-stage sequence, and the order is load-bearing because of a trap in your own RLS design.

**Stage one — plumbing, before any column moves.** The branch context is already signed into the JWT by `switchContext` (`auth/auth.service.ts:200-205`) and surfaced on the request by `jwt.strategy.ts:62-65`, and then it is *thrown away*: `TenantMiddleware.buildContext` rebuilds `TenantCtx` with only `tenantId`, `userId`, `role` and `isPlatformAdmin` (`common/tenant/tenant.middleware.ts:54-59`, interface at `tenant-context.ts:19-27`). No service anywhere can see the branch. Extend `TenantCtx` with `branchId` and `departmentId`, stop discarding the claim, and add an `app.branch_id` GUC set alongside `app.tenant_id` inside `PrismaService.forTenant` (`common/prisma/prisma.service.ts:181`). Doing this first means the columns can be populated automatically the moment they exist, rather than requiring twenty-five services to be edited by hand. Roughly one week.

**Stage two — nullable columns and application-level population.** Add `branchId String? @db.Uuid` plus a composite index `@@index([tenantId, branchId])` to approximately 28 tables. In priority order, because the clinical damage is worst first: `StockItem` and `VaccineBatch` (a two-branch clinic sharing one stock row will show inventory at a site that does not have it, and a cold-chain excursion will be attributed to the wrong fridge), then `Invoice`, `InvoiceLineItem`, `Payment`, `Refund`, then `Patient`, `Appointment`, `Encounter`, `TreatmentPlan`, then `Employee`, `PayrollRun`, `Payslip`, then `Lead`, `LabOrder`, `ImagingOrder`, `Dispense`, `Admission`, `Ward`, `Bed`, `AuditLog`. Backfill every row to the tenant's `MAIN` branch — the one already created at onboarding (`platform-tenants.service.ts:230-239`). The composite indexes matter as much as the columns; without them every branch dashboard is a full table scan. Roughly three weeks.

**Stage three — the RLS policies, and this is where the trap is.** Your codebase documents it already at `platform-tenants.service.ts:22-26`: a Postgres policy with no explicit `WITH CHECK` clause reuses its `USING` expression as the insert check. So the moment you add a branch predicate to a policy, *every write path that has not yet learned to set the branch GUC starts failing* — and it will fail as scattered, unexplained 500 errors in modules that have nothing obvious to do with branches. This is why stage one must come first and must be complete. Roughly two weeks including the verification pass.

**Stage four — `NOT NULL`, and extend the CI guard.** Your `scripts/check-rls-coverage.ts` already fails the build if a tenant table lacks a policy; extend it to assert branch predicates so this cannot silently regress. Roughly one week.

Call it seven to nine weeks of focused work for one engineer who is not doing anything else, on a codebase with no production data. Every month you wait adds backfill guesswork you can never undo. My recommendation is unambiguous: do this before onboarding a second branch or a second clinic, not after.

## 3. What is genuinely right, and must not be thrown away

This section matters as much as the criticism, because a rewrite would destroy real value. Four things in this codebase are better than what most teams ship, and one of them is better than what most *funded* teams ship.

**Tenant isolation is production-grade, and it is the crown jewel.** I counted 86 `ENABLE ROW LEVEL SECURITY` statements and 87 `FORCE ROW LEVEL SECURITY` statements in `prisma/rls.sql`. Every policy uses the fail-closed form `"tenantId" = nullif(current_setting('app.tenant_id', true), '')::uuid`, which returns zero rows rather than all rows when the context is unset — the correct direction to fail. `PrismaService` refuses to start the application at all if the database role it connects with could bypass RLS (`prisma.service.ts:55-77`). Three separate CI guards prevent regression: `check-rls-coverage.ts`, `check-rls-live.ts` and `check-tenant-isolation.ts`. The last of these is the detail that tells me someone here understands security: it connects *as the runtime role* and plants a second tenant's row to prove isolation empirically, rather than reading the schema and self-certifying. That is the difference between a test that proves something and a test that agrees with you. Do not touch this except to extend it.

**The entitlement and editions engine works on both sides and is honestly enforced.** `EntitlementGuard` (`entitlements/entitlement.guard.ts:20-50`) is applied via `@RequiresEntitlement` on 25 controllers, it requires an explicit `enabled === true` row and never defaults to allow, and there is a CI script (`check-entitlement-coverage.ts`) keeping coverage from drifting. The frontend hides unpurchased modules through `filterNav` (`app/web/src/layout/nav.ts:86-95`). This is exactly the right shape for a modular SaaS. It has two commercial problems worth fixing — the keys are too coarse (`integrations.core` bundles WhatsApp, FBR and telehealth into one all-or-nothing purchase; `hr.core` reaches only the HOSPITAL and ENTERPRISE editions, so your actual dermatology client cannot see payroll at all), and entitlements are written exactly once at onboarding with no route to change them afterwards. But those are configuration and CRUD problems on top of a correct mechanism. Keep the mechanism.

**The pack manifest system is the right idea, correctly typed.** `manifest.types.ts` defines a versioned, validated authoring format; `requiresEntitlements` is deliberately non-optional so a pack fails closed; `pack-seeding.ts` expands a manifest into tenant-scoped rows idempotently inside a single RLS-scoped transaction. Six manifests exist. This is a genuinely good foundation — it is simply not yet connected to a renderer, and I will come to that.

**The safety discipline is unusual and valuable.** There are 26 adversarial HTTP suites in `test/safety/` and eleven CI guard scripts in `scripts/`. More telling than the count is the quality of thinking in the source comments. `billing.service.ts` documents why invoice numbering takes an advisory lock. `dermatology/engines/phototherapy.engine.ts:15-47` documents *three successive generations* of a dosing engine that each produced more UV light for a worse skin reaction, and states the invariant that finally fixed it: every applicable rule contributes a candidate, the most conservative wins, there are no early returns, and there is a single clamp at a single exit. `emr.service.ts:201-208` documents a treatment plan that re-entered `PROPOSED` and was invoiced three times for 240,000 PKR, and the state machine that now prevents it. This is a team that has learned from real failures and written the lessons where the next person will find them. That culture is worth more than any individual feature and must survive whatever refactoring happens.

One caveat on that last point, in the spirit of your own note about green suites certifying broken code: the discipline is applied unevenly. There is no safety suite anywhere touching `UserMembership`, `/auth/contexts`, `/auth/switch-context` or `/org/hierarchy` — which is precisely why the escalation at the top of this document survived. The discipline is right; its coverage map has a hole exactly where the newest code is.

## 4. Branch and department: what breaks, and what to do about the parts that are not just columns

I have covered the migration sequence above. Here I want to address the three things that break in ways a column migration does *not* fix, because these are the parts a team will discover halfway through and be forced to decide under pressure.

**The first is that `User` is single-tenant while the switcher is cross-tenant, and they contradict each other.** `User.tenantId` is a single scalar (`schema.prisma:221`), `User.email` is globally unique (`:222`), and `User` itself carries a tenant-keyed RLS policy (`rls-user.sql:35-42`). Meanwhile the whole point of the hierarchy is one owner holding memberships in three clinics. The moment a genuine cross-tenant membership exists, the acting user's own `User` row becomes invisible in the clinic they switched into. This is not theoretical: `org-hierarchy.service.ts:30-38` selects `user: { ... }` on a *required* Prisma relation, so a cross-tenant membership makes `GET /org/hierarchy/summary` throw "Field user is required to return data, got null." One of these two designs has to move before you have a single multi-clinic customer. My recommendation is to make `User.tenantId` mean "home tenant" only and let memberships be the authority on access — but the decision must be explicit, not discovered.

Note also that today there is **no API anywhere that can create a cross-tenant membership.** `createMembership` pins the clinic to the caller's own tenant (`org-hierarchy.service.ts:108-112`), `CreateMembershipDto` has no `clinicId` field, every onboarding mints a brand-new `Organization` (`platform-tenants.service.ts:207-229`), and `CreateTenantDto` has no `organizationId`. So the headline scenario in your brief — one owner, three clinics, one login — cannot be produced by any sequence of API calls. The clinic switcher renders only when `contexts.length > 1` (`AppShell.tsx:182`), which is unreachable for every user in the system including the seeded demo owner. The switcher is well-built and has never once been displayed.

**The second is that branch-level access control has no enforcement layer to hang on.** Once invoices carry a branch, a branch manager who must not see another branch's payroll needs row-level scoping, and your RBAC is a flat Prisma enum checked by a guard that compares one string (`rbac/roles.guard.ts:38`). There is no permission table, no scope concept, and `UserMembership.branchId` is written but read by nothing outside the hierarchy service. Adding the column without the scoping means every branch's payroll is visible to every FINANCE user in the tenant. Plan the enforcement layer as part of the migration, not after it.

**The third is the organization tier itself, which your current RLS design makes unqueryable from inside a clinic.** The `Organization` policy (`rls.sql:614-622`) reveals an organization only through an `OrganizationClinic` row matching the *current* `app.tenant_id`. So a consolidated dashboard, org settings, an org-wide staff directory and org-level audit cannot be served from an ordinary `forTenant()` transaction at all. The existing escape hatch is `SECURITY DEFINER` functions, and `rls-user.sql` already has three, with a comment in the file saying — correctly — that it should stay that way because every addition is another thing running as the database owner. The brief asks for a whole org-admin surface, which on the current design means a dozen such functions, each a hand-audited hole. The better answer is a second GUC, `app.organization_id`, set from a validated membership, with org-tier policies keyed on it: one mechanism to audit instead of N functions. Decide this before the first org-level endpoint is written.

## 5. The specialty pack question: what a true configuration engine looks like here

The right question is not "config engine or hard-coded tables." It is *which* clinical content is a form and which is a domain model. Getting that line right is the whole answer, and I think a strict either/or would be a mistake in both directions.

Some of what is currently hard-coded genuinely earns its tables. The WHO-LMS growth engine, the weight-based paediatric dose calculator with its medico-legal `DoseCalculationLog` (`schema.prisma:2077`), the partogram alert logic, the phototherapy dose engine with the hard-won invariant documented at `phototherapy.engine.ts:15-47` — these carry real mathematics and real safety properties. Their data is queried, charted, graded and reasoned over. Trying to express them as generic JSON forms would be a regression, and in the phototherapy case an actively dangerous one.

But a great deal of what is currently hard-coded is *just a form someone fills in*. `GynaeProfile` (`schema.prisma:2046`), `MskAssessment` (`:2534`), `PerioToothRecord` (`:2173`), `EyeSegmentFinding` (`:2433`) are structured questionnaires that happened to be given tables and enums because that was the path of least resistance. Every one of them cost a migration, a module, a controller and a hand-written React page. That is where the five-to-one ratio comes from, and that is what a real configuration engine absorbs.

### What is missing to make Layer 2 real

Three things, and only one of them is large.

**A form definition model with a lifecycle, which does not exist.** There is no `FormTemplate`, no versioning, no publish state, no binding. `NoteTemplate` (`schema.prisma:1311`) and `IntakeFieldGroup` (`:1329`) are pack-seeded JSON blobs with no `version`, no `status`, and no `branchId`/`departmentId`/`roleId` to bind against. The field-type vocabulary in `manifest.types.ts:11-18` has seven types — no image, no file upload, no digital signature, and no conditional visibility — and three of those four are explicit requirements in your brief. Digital signature in particular appears nowhere in the entire repository except on `EyeExam` (`schema.prisma:2355-2356`), meaning sign-off was solved once for ophthalmology and never generalised. A clinical record with no signature and no lock has weak medico-legal standing.

**A write path, which does not exist at all.** I grepped every create, update, upsert and delete against the six config tables across the whole backend. There are exactly five, and all five are in `packs/pack-seeding.ts` (lines 37, 63, 83, 98, 134). No tenant, no clinic admin, and no platform admin can create or edit a form, a service price, an order set or a dose rule through any endpoint. The `CatalogController` is 102 lines of read-only routes. This directly contradicts your own plan document's definition of done ("configurable by admins without code deployment").

There is a trap waiting here that must be solved *with* the builder rather than after it: `seedPackForTenant` upserts and overwrites `name`, `fields`, `schema`, `items` and chart bands on every activation, and the comment at `pack-seeding.ts:121-122` candidly admits "a tenant edit survives until the pack is re-activated." The day a clinic can customise a form is the day a routine pack version bump silently destroys every clinic's customisations. You need a copy-on-write model with a `source`/`isCustomised` discriminator before the first editable field ships.

**A generic renderer in the React application, which does not exist.** This is the piece that would make the other two worth having. The legacy static page `app/backend/public/aesthetic-workspace.html:169-181` already contains a working generic renderer that walks intake groups and note-template sections and produces fields. The React port left it behind. So the system's configuration capability has actually *regressed* relative to its own earlier demo, and today the only definition-driven screen in the product is `TrendsPage.tsx`.

### Rules as data, and the one thing that must not be done naively

Your brief asks for configurable clinical rules — dose limits, session intervals, contraindications, required consent, required tests, age restrictions. Today every one of these is compiled TypeScript: the phototherapy protocol is a literal object at `phototherapy.engine.ts:90-92`, the electrotherapy contraindication list is a hard-coded array at `rehab/engines/modality-safety.ts:37-56`, the ANC and partogram alerts are their own engines. There is no `ClinicalRule` table and no shared execution log, so a warning fired in rehab or obstetrics exists only in an HTTP response and is never recorded — meaning "which warnings did the doctor see and override, and why" is unanswerable for most of the product.

If you build a generic rule evaluator, it **must** adopt the phototherapy engine's contract as its combination semantics: every applicable rule contributes a candidate, the most conservative candidate wins, no rule may return early, and there is exactly one clamp at exactly one exit. A conventional first-match-wins or priority-ordered rule engine would reintroduce, across every specialty at once, precisely the class of bug that file documents three generations of. And the dermatology safety suite must be re-run against the generic path before the hard-coded engine is deleted. This is the single highest-risk piece of work in the whole plan, and it should not be scheduled as "a sprint."

### Can the two coexist? Yes — and they must

Absorption should be selective and gradual, not a rewrite.

The forms layer absorbs the questionnaire-shaped tables. `GynaeProfile`, `MskAssessment`, the perio chart, the eye segment findings — these become `FormTemplate` definitions with submissions, retiring perhaps a dozen of the thirty specialty tables and a large share of the 47 specialty enums along with them. The vocabularies that are currently Prisma enums become seeded lookup rows, so adding a term stops being a migration.

The domain layer keeps what carries mathematics and safety invariants: growth, dosing, partogram, phototherapy, the cold chain. These stay as tables and engines, but they should be *registered* through the pack system rather than wired into `App.tsx` and `nav.ts` by hand. `manifest.types.ts:87-91` already defines `PackWidget { key, route, name }` for exactly this purpose — and it is read by nothing. Six manifests declare widgets; none of those routes exist in the router. Making the navigation derive from activated packs plus their widgets is a modest piece of work that immediately removes two frontend source edits from every future specialty.

The realistic target is not "zero specialty code." It is: a new dermatology or dental clinic onboards with *zero* code changes, because forms, prices, order sets, terminology, diagnosis lists and rules are all data; and a genuinely new clinical *engine* — something with new mathematics, like a cardiology risk score — is a bounded plug-in that registers itself through a manifest rather than a core rebuild. That target is reachable from where you are. It is not reachable by adding a seventh specialty in the current style.

## Sequencing, plainly

Fix the privilege escalation this week — it is small, it is exploitable today, and it exposes every clinic on the platform to every other clinic's owner.

Then do the branch and department migration, together with `InvoiceLineItem.performedById` and `Employee.userId`, before you take on a second branch or a second clinic. Everything else in your brief can be built later at the same cost. This one gets permanently more expensive with every row written.

Then connect Layer 2 to the product — the generic renderer, the write path, the copy-on-write rule — because until the React application reads a single line of pack configuration, the entire configuration engine is a well-built thing that no customer can see.

Do not rewrite. The tenant isolation, the entitlement engine, the pack format and the safety discipline are the assets. The problem is not that the foundation is wrong; it is that the second floor was built beside the building instead of on top of it, and nobody has yet moved in.
